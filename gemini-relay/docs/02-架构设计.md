# 02. 架构设计

> 本文是什么：中转方案的设计目标、备选方案取舍、请求生命周期与 Worker 代码的逐条设计决策。
> 读者何时读：部署前想清楚"为什么这样设计"，或评审代码时对照决策依据。

## 1. 设计目标与约束

- **同事零配置：中转地址内置在 provider 代码里（v2）。** v1 曾以"不改动
  `coworker/providers/gemini_provider.py` 原代码"为约束、靠环境变量
  `GOOGLE_GEMINI_BASE_URL` 接线；v2 解除该约束——`gemini_provider.py` 顶部内置模块常量
  `RELAY_BASE_URL = "https://gemini.smjtools.com"`，`_ensure_client()` 构造 `genai.Client`
  时显式传 `http_options=types.HttpOptions(base_url=resolve_base_url(...))`。
  `resolve_base_url()` 的优先级：profile 隐藏 `base_url` 覆盖（`registry.py` 的
  `_build_gemini`，UI 不出现该字段）→ 环境变量 `GOOGLE_GEMINI_BASE_URL`（调试通道）→
  内置常量。同事在 UI 里只填 API key，不需要任何环境变量（v1 的环境变量机制记录在
  [04-OpenWorker接入.md](./04-OpenWorker接入.md)，现为调试参考）。
- **按人准入与记账。** 身份来自服务端而非客户端自报：同事走 Cloudflare Access 一次性
  验证码登录，Worker 验签 Access 断言拿到邮箱、查 KV 名单，然后签发一个只对本中转有效的
  令牌（v3；v2 是 `sha256(api_key) → 邮箱` 的 key 哈希名册）。调 Google 用的 Gemini key 则
  由管理员按人签发、同事自己填，随请求头原样透传，**中转一把都不存**。名单同时充当准入控制（没令牌 401、令牌失效 403）。每次请求把
  响应流 `tee()` 出一支，`ctx.waitUntil` 后台解析 usageMetadata 并异步写入 D1 `usage` 流水表，
  绝不拖慢已返回客户端的响应。名册与报表的完整说明见
  [07-多用户与用量统计.md](./07-多用户与用量统计.md)。
- **中国大陆可直连。** 中转必须挂在自定义域名上，不能用 `*.workers.dev`——社区多个帖子报告
  `*.workers.dev` 在中国大陆被 DNS 层污染或连接重置（研究 JSON `cloudflare.findings`
  "China reachability - workers.dev blocked"，证据
  `https://community.cloudflare.com/t/worker-is-not-available-in-china/497419`）。
- **流式必须增量到达。** Gemini 的 `streamGenerateContent?alt=sse` 依赖 SSE 分块到达；Worker
  直接透传 `upstream.body`（`ReadableStream`），不做任何缓冲或拼接。
- **API key 与对话内容不落第三方。** Worker 不打印、不持久化任何请求头或正文（日志输出只有
  三处 `console.error`：D1 写入失败、记录支路整体失败、限额计数读写失败，均不含请求内容）；
  D1 里只存用量元数据（邮箱、模型名、token 计数、令牌哈希前 12 位），不存请求体、响应正文，
  也不存任何人的 Gemini key——**中转根本不保存 key**，每个人自己的 key 只是随请求头过一遍
  就转给 Google 了。中转域名与 Worker 都在管理者本人的 Cloudflare 账号下（smjtools.com 由
  他的账号托管，Worker 也部署在同一账号），这是整套信任模型的前提；信任边界与 PII 边界的
  完整讨论见 [06-安全与风险.md](./06-安全与风险.md)。

## 2. 架构与请求生命周期

```
openworker (google-genai 2.16.0, httpx 0.28.1)
   │  HTTPS 直连，SNI = gemini.smjtools.com，无需 v2rayN
   ▼
Cloudflare Worker @ gemini.smjtools.com   ← Custom Domain，自动建 DNS + TLS
   │  1. 校验路径是否在白名单内，否则 404
   │  2. 取登录令牌（只认 Authorization: Bearer），没有 → 401
   │     （拒绝也记一条 D1 流水，email="(no-token)"）
   │  3. 查 KV "t:<sha256(令牌)>" → 邮箱，再查 "u:<邮箱>" 确认还在名单里；
   │     任一步落空 → 403（记流水，email="(revoked)"；两次查询都带 cacheTtl:300 边缘缓存）
   │  3b. 取调用方自己的 Gemini key（x-goog-api-key，其次 ?key=），没有 → 400
   │  3c. 限额闸门：按邮箱查 D1 quota 表的分钟桶/日桶，超了 → 429 + Retry-After
   │      （放行后立刻异步 +1，不等响应结束——长流式请求也要先占住位置）
   │  4. 剥离 hop-by-hop / cf-* / 转发相关请求头，以及我们自己的 Authorization
   │  fetch(UPSTREAM + pathname + search, {redirect: "manual"})
   ▼
Gemini API（generativelanguage.googleapis.com，出口 IP 为 Cloudflare 边缘）
   │  响应原样回传，剥离 content-encoding/content-length、加 cache-control: no-transform；
   │  upstream.body.tee() 一分为二：客户端支路直接流式转发（SSE 增量、不等待解析），
   │  记录支路交 ctx.waitUntil(recordUsage) 后台消费——解析 usageMetadata
   │  （SSE 是逐 chunk 累计值，覆盖式取最后一次即总量）→ 异步 INSERT 进 D1 usage 表
   ▼
openworker（同步/流式路径共用同一条链路）
```

非流式 (`generateContent`) 和流式 (`streamGenerateContent?alt=sse`) 走同一个 Worker 逻辑，
**客户端方向仍是全程透传**：路径分类（`kind`/`model` 列）在主请求路径上同步完成——`classify()`
紧跟在路径白名单校验之后、鉴权与转发之前调用，两条路径共用同一次调用；真正只发生在 `tee()`
出来的记录支路上的是用量解析（`parseSSE`/`parseNonStream` 解析 usageMetadata）。两者都不触碰
返回给客户端的那支流，因此两条路径的行为完全一致（对应 SDK 侧同步/流式共用 `_build_request()`，
见 [01-背景与结论.md](./01-背景与结论.md) 第 2.1 条）。CPU 时间只
计入 Worker 主动执行 JS 的时间，等待 Gemini 上游返回（含流式等待）不计入免费版 10ms CPU
时间预算（研究 JSON `cloudflare.findings["Free plan limits relevant to an LLM relay"]`，证据
`https://developers.cloudflare.com/workers/platform/limits/`）。记录支路的 JSON 解析计入
CPU，但代码做了大 body 保护：非流式 body ≥1MB 时不做全文 `JSON.parse`，改从尾部
`lastIndexOf("usageMetadata")` 括号配平提取小对象；单个 SSE 事件 >4MB 直接跳过解析。

## 3. 备选方案对比

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 纯 Worker 反向代理（选定）** | 单文件 `fetch` handler，路径白名单 + 头部清理 + 透传到 `generativelanguage.googleapis.com`，挂 Custom Domain | 无需 Cloudflare Access，无沙箱依赖，直接命中官方 REST 形状 |
| B. Cloudflare AI Gateway | 原生 "Google AI Studio" provider，支持自定义域名 | 排除。**事实更正（2026-08 复核）**：本表早先版本称"自定义域名场景下文档明确要求配合 Cloudflare Access"，该结论已过时——按 2026-08 的 Cloudflare 文档，自定义域名**不再强制** Access。仍然不选它的理由：免费版日志总量上限 10 万条（不是每天，是总量）；请求路径是 provider 专属前缀，与 SDK 原生 REST 路径形状不一致；BYOK 需把 key 托管给 Cloudflare。自建 Worker 三者皆无 |
| C. `@cloudflare/computer` http-gateway | `WorkspaceEgressPolicy` + `globalOutbound`/`interceptOutboundHttp(s)` | 排除：机制错位，服务对象是沙箱执行后端（容器/Dynamic Worker）的出口管制，不是公网 API 中转，引入会多背 Durable Object/container/worker_loaders 绑定却无收益（研究 JSON `computer.recommendations[2]`）；但其 `EgressGateway` 的白名单+透传写法被借鉴到方案 A 里 |
| D. 继续用 v2rayN 正向代理（早期方案） | v2rayN + proxy-guard，`HTTPS_PROXY` 等环境变量 | 保留作为回退：已验证可用，但依赖本地代理进程常驻，且影响所有 provider 的出口路径（对比详见 [01-背景与结论.md](./01-背景与结论.md) 第 3 节） |

## 4. computer 仓库 egress 机制一节（为什么不引入 `@cloudflare/computer`）

`examples/egress` 定义了 `WorkspaceEgressPolicy` 的三种模式（研究 JSON `computer.findings[0]`，
证据 `examples/egress/src/egress.ts:7-18`）：

| 模式 | 效果 |
|---|---|
| `none` | `{mode:'none'}`，禁止出网 |
| `direct` | `{mode:'direct'}`，允许原生出网 |
| `http-gateway` | `{mode:'http-gateway', gateway, revision}`，经一个 `Fetcher` 网关转发 |

`http-gateway` 模式在两类执行后端上的实现机制不同，但对"网关看到什么"这个问题答案一致：

- **`worker-javascript` / `worker-shell` 后端**：网关通过 Cloudflare Worker Loader 的原生
  `globalOutbound` 绑定选项接管 `fetch()`——这是 JS 绑定层的替换，不经过真实网络跳转，网关
  收到的 `Request.url` 就是真实目标地址（研究 JSON `computer.findings[3]`，证据
  `packages/computer/src/backends/worker-javascript/worker-javascript.ts:190-200,953`）。
- **`container` 后端**：通过 Cloudflare Containers 平台原生的
  `interceptOutboundHttp`/`interceptOutboundHttps`/`interceptAllOutboundHttp` 方法拦截容器的
  出网调用，中间经一次内部 `WorkspaceProxy` 跳转（临时用 `x-workspace-egress-token` /
  `x-workspace-egress-url` 两个头编码真实目标），在到达用户提供的网关 `Fetcher` 之前，这两个
  头会被拥有者 Durable Object 剥离并重建为普通 `Request`（研究 JSON `computer.findings[4]`，
  证据 `packages/computer/src/backends/container/cloudflare-container.ts:271-274,379-399`、
  `container-host.ts:256-278`、`proxy.ts:66-79`）。

两种路径下，网关 `Fetcher` 拿到的都只是明文 JS `Request`/`Response` 对象，从未接触过原始
TLS 字节，网关必须自己对真实目标发起一次新的出站 `fetch()`（自己的 TLS 握手）——这正是
`examples/egress/src/index.ts:34-44` 里 `EgressGateway.fetch()` 用
`fetch(request, {redirect:'manual'})` 做的事（研究 JSON `computer.findings[4]`）。

这套机制的服务对象是"`@cloudflare/computer` 自己跑起来的沙箱代码（容器或 Dynamic Worker）
能不能出网"，不是"外部客户端能不能公开访问某个 Worker"——`EgressGateway` 本身也只能通过内部
`Fetcher` 绑定调用，从未挂过公网路由（研究 JSON `computer.findings[8]`，证据
`examples/egress/src/index.ts:47-49`）。本方案的场景是外部 Python 进程直接对公网 Custom
Domain 发起 HTTPS 请求，不存在 Workspace、Durable Object 或沙箱执行后端，因此不需要
`@cloudflare/computer` 这个依赖；`EgressGateway` 的白名单 + `redirect:'manual'` 透传写法作为
设计参考，被吸收进本方案的 Worker 代码里。

## 5. Worker 设计决策逐条

以下逐条对应 `worker/src/index.ts` 的实际代码（完整代码见
[03-Worker部署指南.md](./03-Worker部署指南.md) 引用的源文件）。

**路径白名单（防止开放代理化）**

```ts
const ALLOWED_PATH = /^\/(upload\/)?(v1|v1beta|v1alpha)\//;
```

google-genai SDK 只会调用 `/v1beta/...`（默认 `api_version`）；`/upload/` 预留给 Files API。
不匹配的路径（扫描器、拼写错误）一律返回 `404 not found`——不给出上游是什么的任何线索。

**上游地址硬编码**

`UPSTREAM = "https://generativelanguage.googleapis.com"` 是常量，请求路径只用来拼接
`pathname + search`，客户端无法通过请求改写实际转发目标。

**请求头黑名单**

```ts
const STRIP_REQUEST_HEADERS = [
  "host", "connection", "keep-alive", "transfer-encoding", "upgrade",
  "proxy-authorization", "te", "trailer",
  "x-forwarded-for", "x-forwarded-host", "x-forwarded-proto",
  "x-real-ip", "true-client-ip",
];
```

剥离 hop-by-hop 头和所有会泄露客户端/边缘细节的头。此外用一个循环把所有 `cf-*` 边缘头
（`cf-connecting-ip`、`cf-ipcountry`、`cf-ray` 等）一并剥离。

**三种非 200 语义**

| 状态码 | 触发条件 | 含义 |
|---|---|---|
| 404 | 路径不匹配 `ALLOWED_PATH` | 路径白名单外，直接拒绝，不暴露上游信息 |
| 401 | 请求没带登录令牌 | 拒绝匿名请求，让中转对随机扫描器没有利用价值，同时不暴露上游是谁。令牌只从 `Authorization: Bearer` 读——完整 URL（含查询串）会进 `wrangler tail` 和 Cloudflare 日志，请求头不会 |
| 403 | 令牌查不到，或它背后的邮箱已不在名单里 | 拒绝的同时仍记一条 D1 流水（email="(revoked)"，带令牌哈希前 12 位） |
| 400 | 登录了，但没带自己的 Gemini key（或带的是登录令牌——旧版客户端会这样） | 宁可明说也不要把空凭证转给上游，让 Google 回一个看起来像是同事自己的问题的 403 |
| 429 | 撞上限额闸门（分钟/每日请求数、每日 token 数，或被管理员置 0 停用） | 带 `Retry-After`。这一条不计入计数器——被拒的请求再消耗额度会变成自我强化的死循环 |

四种拒绝的响应体都是 **Google 自己的错误信封**（`{"error":{"code","message","status"}}`）而不是
纯文本：客户端是 google-genai SDK，它会解析这个结构并把 `message` 放进抛出的异常里。纯文本
body 到用户那儿只剩一段堆栈，而「没填 key」「超额度」恰恰是最需要被读到的两条。`message`
用中文写并且点名「OpenWorker 中转」，免得有人拿着一个不是 Google 设的限额去找 Google。

**限额闸门（quota.ts）**：计数器落在 D1 而不是 KV——KV 没有原子自增，写入还是跨 colo 最终
一致，两个边缘各读到同一个旧值再各写一个 1，counter 就废了。桶按北京时间切（`m|` 分钟、
`d|` 天），每人每天的分钟桶由 Worker 的 cron 定时任务三天后清掉。上限的解析顺序是「名单条目
里的 rpm/rpd/tpd → `wrangler.jsonc` 的 `QUOTA_*` 默认值」，`-1` 不限、`0` 停用。三项都是 `-1`
的人（管理员）连 D1 都不读。已知的不精确之处写在 `quota.ts` 的文件头注释里：请求在**放行时**
计数而不是结束时，token 则要等响应体解析完才补上，所以同一秒内并发启动的一堆长流式请求可能
一起挤过闸门，token 上限总是晚一个请求才触发。这道闸的职责是「发现跑飞的循环」，不是精确计费。

**登录准入（v3；此前是 v2 的 key 哈希名册，更早是 v1 的 `RELAY_TOKEN` 共享密钥，两者
都已删除）**：准入由「Cloudflare Access 一次性验证码 + KV 名单 + Worker 签发的令牌」三段
承担。管理员用 `scripts/roster.ps1`（`-Import`/`-Add`/`-Remove`/`-List`/`-AccessList`）维护
名单，删条目即吊销该邮箱名下**所有设备**的令牌。名单查询带 `cacheTtl: 300` 边缘缓存：
绝大多数请求不触达 KV 中心存储，代价是增删后最长 5 分钟才全量生效。

登录这条链路本身走的是 OAuth 2.0 授权码 + PKCE 的形状（RFC 8252 对原生应用的建议）：
`/login/<sid>` 由 Access 保护、其余路径公开，参数存在服务端会话里而不走 query string
（Access 做路径匹配时不看 query，跳转中还可能改写它），回调只允许本机回环地址。Access
侧的一次性配置见 [08-Access登录配置.md](./08-Access登录配置.md)，安全性推理见
[06-安全与风险.md](./06-安全与风险.md)。名单模型与报表详见
[07-多用户与用量统计.md](./07-多用户与用量统计.md)。

**响应头处理：剥离 content-encoding/content-length，加 cache-control: no-transform**

```ts
respHeaders.delete("content-encoding");
respHeaders.delete("content-length");
respHeaders.set("cache-control", "no-transform");
```

Workers 的 `fetch()` 会自动解压上游响应体；如果原样保留上游的 `content-encoding`/
`content-length`，转发给客户端时这两个头会与实际（已解压的）body 不匹配，是经典的
"代理 Worker 数据损坏" bug。Cloudflare 会根据客户端的 `Accept-Encoding` 自行重新压缩，
不需要 Worker 手动处理。

`no-transform` 则是反方向的保险：Cloudflare 边缘的自动压缩在某些情况下会为了计算长度
而整体缓冲流式响应，把 SSE 从增量到达变成一次性到达（社区多次报告过该模式，如
cloudflare/workerd#5112 关联讨论）。`Cache-Control: no-transform` 是 Cloudflare 内容压缩
文档明确给出的禁用变换手段，加上后边缘不再压缩/缓冲这条响应，流式增量不依赖
"默认可压缩类型列表恰好不含 text/event-stream" 这种可变假设。

**`redirect: "manual"`**

与 `examples/egress` 里 `EgressGateway.fetch()` 的写法一致（本文档第 4 节），Worker 不代替
客户端跟随上游的重定向，而是把 3xx 响应原样返回，避免掩盖上游的真实行为。

**流式透传 + tee 记账**

`upstream.body.tee()` 把上游 `ReadableStream` 一分为二：客户端支路
`return new Response(clientBody, {...})` 原样返回，不做任何缓冲、拼接或 JSON 解析——这是
保持 SSE 增量到达的关键（对应设计目标里的"流式必须增量"）；记录支路交给
`ctx.waitUntil(recordUsage(...))` 在后台独立消费，解析 usageMetadata 后异步 INSERT 进
D1（`recordUsage` 整体包 try/catch，任何失败都不影响已经发出的响应）。SSE 解析按空行切
事件时兼容 LF 与 CRLF 两种行尾——Google 前端发的是 CRLF，只搜 `\n\n` 会导致整条流粘成一个
解析不了的"事件"。

**不落请求内容日志**

Worker 不 `console.log` 任何请求头或正文；唯一的日志输出是 `console.error`——D1 写入或
记录支路整体失败时打一行错误（`wrangler tail` 可见，用于排查记账问题），错误行里没有
API key 或对话内容。威胁模型细节见 [06-安全与风险.md](./06-安全与风险.md)。

**`workers_dev: false`**

```jsonc
"workers_dev": false,
"routes": [{ "pattern": "gemini.smjtools.com", "custom_domain": true }]
```

`*.workers.dev` 在中国大陆被社区报告为 DNS 层污染（本文档第 1 节），同时它会额外暴露一个不受
控制的第二个可访问域名；关闭它、只服务于自定义域名，把可攻击面收敛到一个入口。
