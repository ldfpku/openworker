## 1. 问题回顾

openworker 调用 Gemini API 时直接报错：

```text
400 FAILED_PRECONDITION
{'message': 'User location is not supported for the API use.', 'status': 'FAILED_PRECONDITION'}
```

浏览器访问 Gemini 网站却正常。`.research/README.md` 已定位根因：Google 按**请求来源出口 IP**
做地区限制；浏览器流量走了 v2rayN 的 SOCKS5 代理（`127.0.0.1:10808`），出口 IP 落在受限地区之外，
而 openworker 的 `coworker/providers/gemini_provider.py` 创建 `genai.Client` 时不带任何代理/URL
选项，只能直连，因而复现该错误（`.research/README.md` 第 17-29 行）。

`.research/test_proxy.py` 的实测结果（`.research/README.md` 第 39-49 行）：

| 出口方式 | 结果 |
|---|---|
| 直连（无代理） | 400 FAILED_PRECONDITION（复现问题） |
| `socks5://127.0.0.1:10808` | 成功，3.6s 返回 |
| `http://127.0.0.1:10809` | 连接拒绝（v2rayN 未开 HTTP 端口） |

当前生产环境用的是 `.research/proxy-guard` 方案：`proxy-guard.ps1` 自动探测本地代理客户端端口、
握手验证后把 `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` 连同约 80 条 `NO_PROXY` 白名单写成 User 级
持久环境变量，并注册定时任务在代理进程下线时自动清空这些变量，避免卡死在失效代理上（研究 JSON
`wiring.findings[9]`，证据 `.research/proxy-guard/README.md:1-211`、`proxy-guard.ps1:553-579`）。
这条路径依赖 v2rayN 常驻、httpx 的 `trust_env=True` 自动读取代理环境变量、以及 `socksio` 包
（`.research/README.md` 第 31-37 行）。它能稳定工作，但需要本地代理进程一直在线。

## 2. 本次研究新增结论

1. **SDK 有原生的反向代理入口，不是只能靠正向代理。** google-genai SDK 在
   `google/genai/_base_url.py:34-50` 里实现 `get_base_url()`，按优先级读取
   `HttpOptions.base_url` → `genai.set_default_base_urls()` → 环境变量 `GOOGLE_GEMINI_BASE_URL`
   （Vertex 家族对应 `GOOGLE_VERTEX_BASE_URL`）。同步 `generate_content` 与流式
   `generate_content_stream` 走同一个 `_build_request()`，两者对 base_url 的处理完全一致
   （研究 JSON `sdk.findings[3]`，证据 `_api_client.py:1309-1414`、`models.py:5028-5030`、
   `models.py:5136-5138`）。

2. **openworker 零注入点：不改一行代码，环境变量即生效。** `coworker/providers/gemini_provider.py:429`
   是 `self._client = genai.Client(api_key=key)`，不传 `http_options`；全仓库也没有任何地方调用
   `set_default_base_urls()`。因此 `GOOGLE_GEMINI_BASE_URL` 环境变量在优先级链上直接生效
   （研究 JSON `wiring.summary`，证据 `gemini_provider.py:418-430`）。同时确认了两个常见误区：
   `state_dir/.env` 只用于解析 `SecretStore` 里 `${VAR}` 占位符，**不会**导出进程环境
   （`coworker/secrets.py:46-56、122-140`）；Tauri 桌面端 sidecar 继承父进程环境
   （`surfaces/gui/src-tauri/src/lib.rs:1-15、628-639`），所以 OS 级环境变量对 CLI、
   `openworker-server`、桌面端三者同等生效。

3. **`@cloudflare/computer` 的 egress 机制定位不同，本方案不需要它。** `examples/egress` 里的
   `EgressGateway`（origin 白名单 + `fetch(request, {redirect:'manual'})`）在概念上就是一个
   反代 Worker，但它只能通过内部 `Fetcher` 绑定被调用，不是公网路由
   （研究 JSON `computer.findings[1]`，证据 `examples/egress/src/index.ts:34-44`）。
   `WorkspaceEgressPolicy`/`globalOutbound`/`interceptOutboundHttp(s)` 这套机制管的是
   "沙箱执行后端（容器或 Dynamic Worker）能不能出网"，服务对象是 `@cloudflare/computer` 自己
   跑的 agent 代码，不是给外部客户端用的公开中转（研究 JSON `computer.findings[7]`，证据
   `docs/17_isolate_javascript.md:83-99`、`README.md:66-68`）。结论：写一个不依赖
   `@cloudflare/computer` 的独立 Worker 即可，`EgressGateway` 的白名单+透传写法作为参考模板。

4. **Cloudflare 平台事实核实完毕。** `smjtools.com` 已在 Cloudflare NS
   （`norm.ns.cloudflare.com` / `georgia.ns.cloudflare.com`）；Custom Domain
   （`routes: [{pattern, custom_domain: true}]`）会自动建 DNS 记录和 TLS 证书；免费版配额
   100,000 请求/天、10ms CPU 时间/次（流式等待上游不计入 CPU）、请求体上限 100MB、
   每次调用 50 个外部子请求（研究 JSON `cloudflare.findings`，证据
   `https://developers.cloudflare.com/workers/platform/limits/`）。`*.workers.dev` 在中国大陆
   被社区多个帖子报告为 DNS 层污染/连接被重置（中等置信度，无官方声明），自定义域名一般更容易
   访问但不保证（GFW 可做基于 SNI 的域名级封锁），需要实测确认（研究 JSON
   `cloudflare.findings["China reachability"]` 两条，证据社区帖子链接见本文档第 4 节）。

5. **DNS 现状：`gemini.smjtools.com` 尚未创建，待部署 Worker 后自动生成。** 本地
   `Resolve-DnsName gemini.smjtools.com` 返回 NXDOMAIN；裸域名 `smjtools.com` 只有 SOA 记录，
   没有 A/AAAA/CNAME（研究 JSON `cloudflare.findings[1..2]`）。这是预期状态——按
   `02-架构设计.md` 部署 Custom Domain 后会自动补全，验证步骤见
   [05-验证与排错.md](./05-验证与排错.md)。

## 3. 与 `.research` 正向代理方案对比

| 维度 | `.research` 方案（正向代理，v2rayN） | 本方案（反向代理，Cloudflare 中转） |
|---|---|---|
| 本地进程 | 需要 v2rayN 常驻 | 不需要，纯远端 Worker |
| 依赖 | 需要 `socksio`（SOCKS5 支持） | 无新增 Python 依赖 |
| 影响范围 | `HTTPS_PROXY` 是 httpx 全局设置，OpenAI/Anthropic 等其他 provider 的流量也会走这个代理 | `GOOGLE_GEMINI_BASE_URL` 只影响 Gemini 家族请求路径，其他 provider 不受影响 |
| 触发机制 | httpx `trust_env=True` 读取代理环境变量（`.research/README.md` 第 33-37 行） | google-genai SDK 的 `get_base_url()` 环境变量分支（本文档第 2.1 条） |
| 现状 | 已验证可用，作为回退保留 | 待部署验证，见 [05-验证与排错.md](./05-验证与排错.md) |

结论：反向代理中转和正向代理是两套独立机制，互不冲突，可以共存（共存注意事项见
[04-OpenWorker接入.md](./04-OpenWorker接入.md)）。中转方案不需要本地常驻代理进程，
也不会影响其他 provider 的出口路径，因此作为主线推荐；v2rayN + proxy-guard 保留作为回退。
架构与设计取舍详见 [02-架构设计.md](./02-架构设计.md)。
