# 05 - 验证与排错

> 本文是什么：中转部署完成后，用五级验证阶梯逐层确认链路真的打通；出问题时查后面的排错矩阵定位原因。建议在完成 [03-Worker部署指南.md](./03-Worker部署指南.md)（含名册登记）之后、把 openworker 分发给同事之前通读一遍。

## 五级验证阶梯

每一级只验证一个环节，出问题就停在当前级别查排错矩阵，不要跳级排查。

### ① DNS 解析

确认 `gemini.smjtools.com` 已经有真实记录，而不是 NXDOMAIN。

```powershell
Resolve-DnsName gemini.smjtools.com
```

预期：返回一个 A/AAAA（或 CNAME）应答，指向 Cloudflare 的边缘 IP。部署前这条命令会返回 "DNS 名称不存在"（NXDOMAIN）——这是已确认的当前状态，Custom Domain 挂载并等待生效后才会变化。

### ② TLS 与健康检查

确认证书已签发、Worker 已经在处理请求。

```powershell
curl.exe -s https://gemini.smjtools.com/healthz
```

预期：纯文本 `ok`，HTTP 200（对应 `worker/src/index.ts` 里 `/healthz` 分支的固定响应）。这一步能连通就说明 TLS 握手、Custom Domain 路由、Worker 部署三者都正常，只是还没测到 Gemini 上游。

### ③ REST 裸调用

跳过 SDK，直接用 REST 验证「中转 → Gemini」这一段，路径必须和 SDK 生成的完全一致：`/v1beta/models/{model}:generateContent`。**两个头都要带**：`Authorization` 是登录令牌（中转消费掉），`x-goog-api-key` 是你自己的 Gemini key（原样转给 Google）。

```powershell
curl.exe -s -X POST "https://gemini.smjtools.com/v1beta/models/gemini-3.5-flash-lite:generateContent" `
  -H "authorization: Bearer $env:OPENWORKER_RELAY_TOKEN" `
  -H "x-goog-api-key: $env:GEMINI_API_KEY" `
  -H "Content-Type: application/json" `
  -d '{"contents":[{"parts":[{"text":"hi, reply with one word"}]}]}'
```

预期：返回 Gemini 的正常 JSON 响应（`candidates` 字段），不是 400 `FAILED_PRECONDITION`。

**前提**：登录令牌背后的邮箱必须在名册里（`scripts\roster.ps1 -List` 可查），否则 403。少带 `x-goog-api-key` 会得到一条中文的 400，少带 `authorization` 会得到 401——两条错误文案会直接说缺哪个。

两个值都用环境变量而不是打在命令里——PowerShell 的命令历史会完整保存你敲过的每一行，凭证字面量一旦出现在命令中就会被记录到 `(Get-PSReadlineOption).HistorySavePath` 指向的文件里。提前在当前会话设好 `$env:GEMINI_API_KEY` 和 `$env:OPENWORKER_RELAY_TOKEN`（后者可以从已登录机器的 `%APPDATA%\coworker\secrets.json` 里的 `provider:gemini.relay_token` 取）。

### ④ SDK 脚本

验证 google-genai SDK 指向中转后，非流式和流式两条路径都正常，且流式确实是增量到达。（`test_relay.py` 是独立诊断脚本，在自己进程内设 `GOOGLE_GEMINI_BASE_URL` 指向中转——这只影响它自己；openworker 本体在 v2 中靠 `gemini_provider.py` 内置常量，不需要这个变量。）

```powershell
& "C:\Users\liude\AppData\Local\hermes\hermes-agent\venv\Scripts\python.exe" gemini-relay\scripts\test_relay.py
```

预期：两个测试都打印 `OK`，退出码 0；流式测试额外打印 chunk 数量与首/末 chunk 的时间差——时间差明显大于 0 说明是增量到达，如果所有 chunk 几乎同时到达，参见下面排错矩阵「SSE 变成一次性到达」一行。

`test_relay.py` 自己会把两个凭证都找齐：登录令牌取自 `OPENWORKER_RELAY_TOKEN` 或已登录机器的 secret store，Gemini key 取自 `GEMINI_API_KEY`/`GOOGLE_API_KEY`/secret store/项目根 `.env`。开头会打印各自的来源（不打印值），并且在跑测试之前先调一次 `/auth/whoami`，把「你是谁 + 今天的限额读数」打出来——少了哪一半、或者已经撞了限额，在第一行就能看见。

**前提**：令牌背后的邮箱要在名册里。想拿 Google 直连做基线对比就加 `--relay https://generativelanguage.googleapis.com`，那条路径只需要 key。

### ⑤ openworker 端到端

跑完前四级说明中转本身没问题，最后确认 openworker 真的在用它。

1. 不需要任何环境变量或脚本——中转地址内置在 `coworker/providers/gemini_provider.py`（`RELAY_BASE_URL` 常量）。在 openworker 的 设置 ▸ 模型 ▸ Gemini 里做两件事：先点「登录」收验证码，再在下面填上自己的 Gemini API key，然后点 Test。Test 会同时带上登录令牌和这把 key，所以它测的就是真实链路。卡片上还会显示今天的限额读数。
2. 用 Gemini 模型发起一次真实对话，流式回复应逐字/逐句出现，而不是等很久后一次性弹出。
3. 不应再出现 `400 FAILED_PRECONDITION`（"User location is not supported"）。

## 「GOOGLE_GEMINI_BASE_URL」自检（v2 中它是调试覆盖，不是接线机制）

v2 的默认中转地址写死在代码里，`GOOGLE_GEMINI_BASE_URL` 只是优先级更高的**调试覆盖**（`resolve_base_url` 的优先级：profile 隐藏覆盖 > 环境变量 > 内置常量）。所以这个自检的用途反过来了：确认本机**没有**遗留的覆盖值把请求指向别处（v1 时代 `set-relay-env.ps1 -Install` 写入的 User 级变量就是这种遗留）。

```powershell
& "C:\Users\liude\AppData\Local\hermes\hermes-agent\venv\Scripts\python.exe" -c "import os; print(os.environ.get('GOOGLE_GEMINI_BASE_URL'))"
```

打印 `None` 是 v2 的**正常状态**（走内置中转常量）；打印出一个值时要确认它就是你想要的调试目标，否则用 `scripts\set-relay-env.ps1 -Uninstall` 清掉。

## 排错矩阵

| 症状 | 可能原因 | 处理动作 |
|---|---|---|
| ① `Resolve-DnsName` 返回 NXDOMAIN | Custom Domain 还没在 Cloudflare 挂载成功，或 DNS/证书正在传播中 | 去 Cloudflare Dashboard 的 Workers 页面确认 Custom Domain 状态；刚 `wrangler deploy` 完通常要等几分钟；参见 [03-Worker部署指南.md](./03-Worker部署指南.md) |
| ② 能解析但连接超时/TLS 握手被重置 | GFW 可能针对该子域名的 SNI 做了定向阻断（自定义域名一般可达但非保证，属中低置信度、需实测的现象） | 换一个新子域名重新走一遍 Custom Domain 流程再测；短期内回退到 v2rayN + proxy-guard 方案（[01-背景与结论.md](./01-背景与结论.md)） |
| ③/⑤ 收到 `404 not found`（纯文本，非 Google 的 JSON） | 请求路径不在白名单内（漏了 `/v1beta` 前缀、拼写错误），或 Worker 部署的是旧代码 | 核对路径必须以 `/v1`、`/v1beta`、`/v1alpha` 开头，或以 `/upload/` 紧跟这三者之一开头（如 `/upload/v1beta/files`；`ALLOWED_PATH` 是 `^\/(upload\/)?(v1\|v1beta\|v1alpha)\/`，裸 `/upload/其他路径` 仍会 404）；重新 `npx wrangler deploy`；用 `npx wrangler tail` 现场看命中的实际路径 |
| ③/⑤ 收到 `401 UNAUTHENTICATED`（中文文案，说「还没有登录」） | 请求没带登录令牌。Worker **只**认 `Authorization: Bearer`——`x-goog-api-key` 那个位置现在归你自己的 Gemini key 了 | 在 openworker 里走一次 **设置 ▸ 模型 ▸ Gemini ▸ 登录**；裸 curl 测试补上 `-H "authorization: Bearer owr_..."` |
| ③/⑤ 收到 `400 INVALID_ARGUMENT`，说「还没有填自己的 Gemini API key」 | 登录成功了，但请求里没有 `x-goog-api-key`（也没有 `?key=`）。中转不持有任何人的 key，这一半必须自己带 | 去 https://aistudio.google.com/apikey 申请一把，填进 **设置 ▸ 模型 ▸ Gemini** 的 API key 输入框。登录卡片上那行红字提示的就是这件事 |
| ③/⑤ 收到 `400 INVALID_ARGUMENT`，说「客户端版本过旧」 | 老版本客户端把登录令牌塞在 `x-goog-api-key` 里发过来了（那是升级前的存法） | 升级 openworker。升级后重新登录一次，令牌会存进新的 `relay_token` 槽位 |
| ③/④/⑤ 收到 `429 RESOURCE_EXHAUSTED`（中文文案，带 `Retry-After`） | 撞上按邮箱的限额闸门。文案会写明是哪一档：每分钟请求数、每天请求数、每天 token 数，或者被管理员置 0 停用了 | 每分钟那档等一分钟即可（一轮带工具调用的 agent 循环十几次请求很正常，容易撞）；每天那档要么等北京时间次日 0 点，要么让管理员调高：`roster.ps1 -Add <邮箱> -Rpd 3000`（重复登记即覆盖）。管理员可以用 `usage_report.py --quota` 看全员当天读数 |
| ③/④/⑤ 收到 `403 relay session expired or revoked`（纯文本） | 令牌过期（30 天）、已注销，或它背后的邮箱已经被移出 KV 名单。注意名单查询带 `cacheTtl: 300` 边缘缓存——刚登记/刚删除的人最长要 5 分钟才在所有边缘生效 | 重新登录一次；仍然不行就让管理员跑 `roster.ps1 -List` 确认该邮箱在名单里（不在就 `-Import`），然后等几分钟再试。名单操作详见 [07-多用户与用量统计.md](./07-多用户与用量统计.md) |
| ⑤ openworker 的 Gemini 栏一直显示「未登录」，或刚登录完就掉回未登录 | 应用启动时会拿存着的令牌向中转要一次 `/auth/whoami`，收到 401/403 就把它丢掉（`coworker/relay_auth.py` 的 `status(verify=True)`）——所以「掉回未登录」等价于上一行的令牌失效 | 同上一行。要区分「令牌真失效」和「中转连不上」：连不上时应用会显示一行连接错误而不是把人登出 |
| ④/⑤ 仍报 `400 FAILED_PRECONDITION`（"User location is not supported"） | v2 默认走内置中转常量，出现这个错误几乎必然是本机遗留的 `GOOGLE_GEMINI_BASE_URL` 调试覆盖把请求指向了 Google 直连或旧地址（该变量优先级高于内置常量） | 用上面的自检命令看当前进程的值；`scripts\set-relay-env.ps1 -Uninstall` 清掉 v1 遗留变量后重启对应进程（新开终端 / 重启 GUI） |
| ④ 流式测试 chunk 几乎同时到达，不是增量 | 中间层压缩/缓冲交互导致（社区已有零星报告，但未定位到 Cloudflare Workers 运行时本身的强制缓冲——中等置信度，非官方文档结论） | 多跑几次 `test_relay.py` 观察是否稳定复现；确认客户端没有额外加压缩选项；持续复现的话记录 `wrangler tail` 输出，和直连 Google 的基线对比 |
| ③ 收到的 `404` 响应体是 Google 的错误 JSON（不是 Worker 的纯文本 `not found`） | 理论上不会发生——Worker 对路径是原样透传（`UPSTREAM + url.pathname + url.search`），不做任何路径改写；出现说明是请求本身的问题 | 核对模型名拼写；确认走的确实是 `v1beta`（google-genai 2.16.0 的默认 `api_version`），不是手误拼成 `v1` |
| ③/④/⑤ 收到 `403`，但响应体是一整页 HTML（标题 `Just a moment...`，含 `_cf_chl_opt`/`cRay`/`challenge-platform/h/b/orchestrate/chl_page` 字样），不是 Worker 的 JSON 错误信封 | 请求在到达 Worker **之前**就被 Cloudflare 边缘的 Bot Management 拦了——zone `smjtools.com` 开着 Bot Fight Mode / Super Bot Fight Mode（或 Security Level 偏高/有挑战类 WAF 规则），把 openworker 这种非浏览器的程序化请求判成可疑流量，弹出 JS/Managed Challenge。这个中转端点本来就是给程序调用的，没有浏览器去解这个挑战，只要开关开着这条路径就永远不通；curl/`test_relay.py` 量小可能不触发，实际 app 高频调用更容易被判为 bot | 登录管理该 zone 的 Cloudflare Dashboard：Security → Bots 关闭 Bot Fight Mode/Super Bot Fight Mode，或更精细地在 Security → WAF → Custom rules 建一条 `Hostname equals gemini.smjtools.com`（可加 `Header x-goog-api-key exists`）→ Skip 挑战类 Managed Rules 的规则，只放行中转端点；顺手检查 Security → Settings 的 Security Level 是否被设成 High/"I'm Under Attack"。这是安全设置变更，只能在 Dashboard 里手动改，改完按第③级重新验证 |

## 登录流程排错

登录这条链路横跨浏览器、Cloudflare Access 和本机回环，失败点比调用链多。**先查 D1 的
`auth_events` 表**——它会告诉你失败发生在哪一段：

```sql
SELECT ts, email, event, detail, country FROM auth_events ORDER BY ts DESC LIMIT 20;
```

表里**根本没有新行** = 请求压根没走到 Worker（Access 拦下了，或者邮箱没过策略）；有
`login-denied` = 过了 Access 但不在 KV 名单里；有 `login-ok` 却没有 `token-issued` =
浏览器那一跳回本机失败了。

| 症状 | 可能原因 | 处理动作 |
|---|---|---|
| 同事说没收到验证码，`auth_events` 里也没有任何记录 | 邮箱不在 Access 策略的 Include ▸ Emails 里。Cloudflare 对被拒的人**照样显示**「验证码已发送」，故意不泄露谁在名单里 | `roster.ps1 -AccessList` 打印应有的邮箱列表，和控制台里的策略核对；顺便让同事看一眼垃圾箱（名单里有几个 QQ 邮箱） |
| 过了验证码，页面显示「这个邮箱不在允许名单里」，`auth_events` 里是 `login-denied` / `not in roster` | Access 策略加了、KV 名单没加。两道闸只动了一边 | `roster.ps1 -Import`（或 `-Add`），等最多 5 分钟边缘缓存过期后重试 |
| 页面显示「身份校验没通过」 | Worker 拿不到有效的 Access 断言。要么 `wrangler.jsonc` 里 `ACCESS_TEAM_DOMAIN`/`ACCESS_AUD` 还是 TODO 占位符或填错，要么 Access 应用被删/改名导致 AUD 变了（AUD 只在删除重建应用时才会变） | 对照 Zero Trust ▸ Access controls ▸ Applications ▸ Configure ▸ Additional settings 里的 AUD 重新填一遍，`wrangler deploy`；`npx wrangler tail` 里会有 "Access verification failed" 和具体原因 |
| 页面显示「登录会话已过期」 | 从点「登录」到填完验证码超过了 10 分钟，或这个链接已经用过一次（会话是一次性的） | 回应用重新点一次「登录」 |
| 验证码填进去说「已被使用」 | 邮箱安全网关会先替用户点一遍邮件里的链接，把一次性码消费掉——这是 Cloudflare 文档里明确提到的已知现象 | 让同事手动输入 6 位码而不是点链接；网关太激进就换一个邮箱 |
| 浏览器停在「无法访问此网站 / 127.0.0.1 拒绝连接」 | 回环那一跳没落地。桌面端每次启动随机绑端口并通过 `COWORKER_PORT` 发布，本机安全软件拦截回环请求、或者中途把 openworker 关了都会这样 | 确认 openworker 还开着，重新点一次「登录」；本机安全软件放行 `127.0.0.1` 的回环访问 |
| 浏览器显示 OpenWorker 的「登录失败」卡片 | 卡片上会带原始错误。`code is unknown, already used, or expired` = 授权码超过 5 分钟或被重放；`verifier does not match the challenge` = 兑换请求不是发起登录的那个进程发的（PKCE 不匹配，通常是中途重启了应用） | 重新点一次「登录」。反复出现就看 `npx wrangler tail` |
| `/auth/session` 或 `/auth/token` 返回一整页 `Just a moment...` 的 HTML | 和下面调用链那条一样，是 Bot Management 拦的。这两个端点是 openworker 后台直接调的，没有浏览器去解挑战 | 见排错矩阵里 Bot Fight Mode 那一行；`/login/*` 是真浏览器所以不受影响，这会造成「登录页能打开、但应用里换不到令牌」的迷惑现象 |
| `curl -i https://gemini.smjtools.com/login/x` 返回 200/404，不是跳转到 Cloudflare 登录页 | Access 应用的 Path 没配成 `login`，或应用根本没建 | 见 [08-Access登录配置.md](./08-Access登录配置.md) 步骤 2。**这是要紧的**：Path 配错成保护整个域名会让 SDK 调用全部失败；完全没保护则会让登录端点失去验证码这道闸（Worker 侧的 JWT 验签会兜住，返回 403） |

## 用量记录（D1）排错

用量流水是 `ctx.waitUntil` 后台写的，任何失败都不影响客户端响应——所以这类问题只能从 D1 数据和 `wrangler tail` 两个侧面发现（用量表 schema 见 `worker/migrations/0001_init.sql`，报表用法见 [07-多用户与用量统计.md](./07-多用户与用量统计.md)）：

| 症状 | 可能原因 | 处理动作 |
|---|---|---|
| usage 表有行，但 token 列全 0 且 `error` 列为 `parse-fail` | 记录支路整体失败（如连接中途重置、流没读完）——请求本身照常记了一行，只是没解析到用量 | 偶发可忽略；持续出现时 `npx wrangler tail` 看 "gemini-relay: recordUsage failed" 的具体错误 |
| usage 表有行，token 列全 0，`error` 列为空 | 部分情形是正常的：`kind` 为 `files`/`models` 的请求没有用量；`embed` 响应按 Google 官方 API 文档只带 `promptTokenCount`（未实测；若上游不带 `usageMetadata`，全 0 也属正常）；`count` 只填 total_tokens；`status` ≥ 400 的失败请求（含 401/403 拒绝行）token 本来就是 0。都不属于这些情形时，说明解析没命中 usageMetadata（响应体形状变化导致的 parse miss） | 先看该行的 `kind` 和 `status` 是否属于上述正常情形；确认是解析缺口的话，对照实际响应体形状检查 `worker/src/index.ts` 的 `fillFromObject` |
| usage 表完全没有新行 | D1 INSERT 在持续失败：最常见是没跑 `wrangler d1 migrations apply ... --remote`（线上没有 usage 表），或 `wrangler.jsonc` 里 `database_id` 还是 TODO 占位符/填错 | `npx wrangler tail` 里找 "gemini-relay: usage insert failed"；补跑迁移或修正 `database_id` 后重新 `wrangler deploy` |

## 回退路径

v2 中 openworker 的 Gemini 流量固定走中转，中转不可用时请求直接失败——**无回退是设计决定**（上游在大陆本就不可达，静默回退只会把失败换一种方式呈现）。紧急调试时可以设 `GOOGLE_GEMINI_BASE_URL` 临时覆盖内置常量、把请求指向别处，但指回 Google 直连需要自行配合 proxy-guard + v2rayN 的正向代理（见 [01-背景与结论.md](./01-背景与结论.md)）；`scripts\set-relay-env.ps1` / `start-openworker-cn.ps1` 属于 v1 遗留脚本，仅在这种调试场景下还有用。
