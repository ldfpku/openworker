# 05 - 验证与排错

> 本文是什么：中转部署完成后，用五级验证阶梯逐层确认链路真的打通；出问题时查后面的排错矩阵定位原因。建议在完成 [03-Worker部署指南.md](./03-Worker部署指南.md)（含名册登记）之后、把 openworker 分发给同事之前通读一遍。

## 五级验证阶梯

每一级只验证一个环节，出问题就停在当前级别查排错矩阵，不要跳级排查。

### ① DNS 解析

确认 `gemini.smjtools.com` 已经有真实记录，而不是 NXDOMAIN。

```powershell
Resolve-DnsName gemini.smjtools.com
```

预期：返回一个 A/AAAA（或 CNAME）应答，指向 Cloudflare 的边缘 IP。部署前这条命令会返回 "DNS 名称不存在"（NXDOMAIN）——这是已确认的当前状态，Custom Domain 挂载并等待生效后才会变化。

### ② TLS 与健康检查

确认证书已签发、Worker 已经在处理请求。

```powershell
curl.exe -s https://gemini.smjtools.com/healthz
```

预期：纯文本 `ok`，HTTP 200（对应 `worker/src/index.ts` 里 `/healthz` 分支的固定响应）。这一步能连通就说明 TLS 握手、Custom Domain 路由、Worker 部署三者都正常，只是还没测到 Gemini 上游。

### ③ REST 裸调用

跳过 SDK，直接用 REST 验证「中转 → Gemini」这一段，路径必须和 SDK 生成的完全一致：`/v1beta/models/{model}:generateContent`，认证走 `x-goog-api-key` 请求头。

```powershell
curl.exe -s -X POST "https://gemini.smjtools.com/v1beta/models/gemini-3.5-flash-lite:generateContent" `
  -H "x-goog-api-key: $env:GEMINI_API_KEY" `
  -H "Content-Type: application/json" `
  -d '{"contents":[{"parts":[{"text":"hi, reply with one word"}]}]}'
```

预期：返回 Gemini 的正常 JSON 响应（`candidates` 字段），不是 400 `FAILED_PRECONDITION`。

**前提**：这个 key 必须已经用 `scripts\roster.ps1 -Add` 登记进名册，否则 Worker 会返回 `403 unregistered key`（v2 的名册准入，见 [07-多用户与用量统计.md](./07-多用户与用量统计.md)）。

用 `$env:GEMINI_API_KEY` 而不是把 key 直接打在命令里——PowerShell 的命令历史会完整保存你敲过的每一行，key 字面量一旦出现在命令中就会被记录到 `(Get-PSReadlineOption).HistorySavePath` 指向的文件里。提前在当前会话 `$env:GEMINI_API_KEY = "<YOUR_GEMINI_API_KEY>"`，或直接复用 openworker 已配置好的同名环境变量。

### ④ SDK 脚本

验证 google-genai SDK 指向中转后，非流式和流式两条路径都正常，且流式确实是增量到达。（`test_relay.py` 是独立诊断脚本，在自己进程内设 `GOOGLE_GEMINI_BASE_URL` 指向中转——这只影响它自己；openworker 本体在 v2 中靠 `gemini_provider.py` 内置常量，不需要这个变量。）

```powershell
& "C:\Users\liude\AppData\Local\hermes\hermes-agent\venv\Scripts\python.exe" gemini-relay\scripts\test_relay.py
```

预期：两个测试都打印 `OK`，退出码 0；流式测试额外打印 chunk 数量与首/末 chunk 的时间差——时间差明显大于 0 说明是增量到达，如果所有 chunk 几乎同时到达，参见下面排错矩阵「SSE 变成一次性到达」一行。

**前提**：和第③级一样，`test_relay.py` 读到的 key（`GEMINI_API_KEY`/`GOOGLE_API_KEY` 环境变量或项目根 `.env`）必须已经登记进名册，否则两个测试都会因 `403 unregistered key` 失败。

### ⑤ openworker 端到端

跑完前四级说明中转本身没问题，最后确认 openworker 真的在用它。

1. v2 不需要任何环境变量或脚本——中转地址内置在 `coworker/providers/gemini_provider.py`（`RELAY_BASE_URL` 常量）。在 openworker 的 Settings ▸ Models 里填入 Gemini API key，点 Test：通过说明 key 已登记且链路可达；报 "This key is not registered with the company relay yet — ask the admin to add it." 说明 key 还没进名册。
2. 用 Gemini 模型发起一次真实对话，流式回复应逐字/逐句出现，而不是等很久后一次性弹出。
3. 不应再出现 `400 FAILED_PRECONDITION`（"User location is not supported"）。

## 「GOOGLE_GEMINI_BASE_URL」自检（v2 中它是调试覆盖，不是接线机制）

v2 的默认中转地址写死在代码里，`GOOGLE_GEMINI_BASE_URL` 只是优先级更高的**调试覆盖**（`resolve_base_url` 的优先级：profile 隐藏覆盖 > 环境变量 > 内置常量）。所以这个自检的用途反过来了：确认本机**没有**遗留的覆盖值把请求指向别处（v1 时代 `set-relay-env.ps1 -Install` 写入的 User 级变量就是这种遗留）。

```powershell
& "C:\Users\liude\AppData\Local\hermes\hermes-agent\venv\Scripts\python.exe" -c "import os; print(os.environ.get('GOOGLE_GEMINI_BASE_URL'))"
```

打印 `None` 是 v2 的**正常状态**（走内置中转常量）；打印出一个值时要确认它就是你想要的调试目标，否则用 `scripts\set-relay-env.ps1 -Uninstall` 清掉。

## 排错矩阵

| 症状 | 可能原因 | 处理动作 |
|---|---|---|
| ① `Resolve-DnsName` 返回 NXDOMAIN | Custom Domain 还没在 Cloudflare 挂载成功，或 DNS/证书正在传播中 | 去 Cloudflare Dashboard 的 Workers 页面确认 Custom Domain 状态；刚 `wrangler deploy` 完通常要等几分钟；参见 [03-Worker部署指南.md](./03-Worker部署指南.md) |
| ② 能解析但连接超时/TLS 握手被重置 | GFW 可能针对该子域名的 SNI 做了定向阻断（自定义域名一般可达但非保证，属中低置信度、需实测的现象） | 换一个新子域名重新走一遍 Custom Domain 流程再测；短期内回退到 v2rayN + proxy-guard 方案（[01-背景与结论.md](./01-背景与结论.md)） |
| ③/⑤ 收到 `404 not found`（纯文本，非 Google 的 JSON） | 请求路径不在白名单内（漏了 `/v1beta` 前缀、拼写错误），或 Worker 部署的是旧代码 | 核对路径必须以 `/v1`、`/v1beta`、`/v1alpha` 开头，或以 `/upload/` 紧跟这三者之一开头（如 `/upload/v1beta/files`；`ALLOWED_PATH` 是 `^\/(upload\/)?(v1\|v1beta\|v1alpha)\/`，裸 `/upload/其他路径` 仍会 404）；重新 `npx wrangler deploy`；用 `npx wrangler tail` 现场看命中的实际路径 |
| ③/⑤ 收到 `401 missing api key` | 请求没有 `x-goog-api-key` 请求头（Worker 只认请求头；`?key=` 查询参数形式被有意拒绝，避免 key 进入 `wrangler tail`/平台日志） | 裸 curl 测试补上 `-H "x-goog-api-key: ..."`；SDK 路径下检查 key 是否真的解析到了（env `GEMINI_API_KEY`/`GOOGLE_API_KEY`，或项目根 `.env`）。SDK 本身只用请求头传 key，不受影响 |
| ③/④/⑤ 收到 `403 unregistered key`（纯文本） | 这个 key 没登记进 KV 名册，或已被吊销。注意名册查询带 `cacheTtl: 300` 边缘缓存——刚登记/刚吊销的 key 最长要 5 分钟才在所有边缘生效 | 管理员跑 `scripts\roster.ps1 -Add <邮箱>` 登记该 key（用 `-List` 核对现有条目）；刚登记完还 403 就等几分钟再试。名册操作详见 [07-多用户与用量统计.md](./07-多用户与用量统计.md) |
| ⑤ openworker 的 Test 按钮报 "This key is not registered with the company relay yet — ask the admin to add it." | 同上一行——`verify_provider_key` 的 gemini 分支现在探测的是中转的 `/v1beta/models`（带 `x-goog-api-key` 头），收到 403 就返回这句话（`coworker/providers/registry.py`） | 同上：登记该 key 后重试 Test |
| ④/⑤ 仍报 `400 FAILED_PRECONDITION`（"User location is not supported"） | v2 默认走内置中转常量，出现这个错误几乎必然是本机遗留的 `GOOGLE_GEMINI_BASE_URL` 调试覆盖把请求指向了 Google 直连或旧地址（该变量优先级高于内置常量） | 用上面的自检命令看当前进程的值；`scripts\set-relay-env.ps1 -Uninstall` 清掉 v1 遗留变量后重启对应进程（新开终端 / 重启 GUI） |
| ④ 流式测试 chunk 几乎同时到达，不是增量 | 中间层压缩/缓冲交互导致（社区已有零星报告，但未定位到 Cloudflare Workers 运行时本身的强制缓冲——中等置信度，非官方文档结论） | 多跑几次 `test_relay.py` 观察是否稳定复现；确认客户端没有额外加压缩选项；持续复现的话记录 `wrangler tail` 输出，和直连 Google 的基线对比 |
| ③ 收到的 `404` 响应体是 Google 的错误 JSON（不是 Worker 的纯文本 `not found`） | 理论上不会发生——Worker 对路径是原样透传（`UPSTREAM + url.pathname + url.search`），不做任何路径改写；出现说明是请求本身的问题 | 核对模型名拼写；确认走的确实是 `v1beta`（google-genai 2.16.0 的默认 `api_version`），不是手误拼成 `v1` |

## 用量记录（D1）排错

用量流水是 `ctx.waitUntil` 后台写的，任何失败都不影响客户端响应——所以这类问题只能从 D1 数据和 `wrangler tail` 两个侧面发现（用量表 schema 见 `worker/migrations/0001_init.sql`，报表用法见 [07-多用户与用量统计.md](./07-多用户与用量统计.md)）：

| 症状 | 可能原因 | 处理动作 |
|---|---|---|
| usage 表有行，但 token 列全 0 且 `error` 列为 `parse-fail` | 记录支路整体失败（如连接中途重置、流没读完）——请求本身照常记了一行，只是没解析到用量 | 偶发可忽略；持续出现时 `npx wrangler tail` 看 "gemini-relay: recordUsage failed" 的具体错误 |
| usage 表有行，token 列全 0，`error` 列为空 | 部分情形是正常的：`kind` 为 `files`/`models` 的请求没有用量；`embed` 响应按 Google 官方 API 文档只带 `promptTokenCount`（未实测；若上游不带 `usageMetadata`，全 0 也属正常）；`count` 只填 total_tokens；`status` ≥ 400 的失败请求（含 401/403 拒绝行）token 本来就是 0。都不属于这些情形时，说明解析没命中 usageMetadata（响应体形状变化导致的 parse miss） | 先看该行的 `kind` 和 `status` 是否属于上述正常情形；确认是解析缺口的话，对照实际响应体形状检查 `worker/src/index.ts` 的 `fillFromObject` |
| usage 表完全没有新行 | D1 INSERT 在持续失败：最常见是没跑 `wrangler d1 migrations apply ... --remote`（线上没有 usage 表），或 `wrangler.jsonc` 里 `database_id` 还是 TODO 占位符/填错 | `npx wrangler tail` 里找 "gemini-relay: usage insert failed"；补跑迁移或修正 `database_id` 后重新 `wrangler deploy` |

## 回退路径

v2 中 openworker 的 Gemini 流量固定走中转，中转不可用时请求直接失败——**无回退是设计决定**（上游在大陆本就不可达，静默回退只会把失败换一种方式呈现）。紧急调试时可以设 `GOOGLE_GEMINI_BASE_URL` 临时覆盖内置常量、把请求指向别处，但指回 Google 直连需要自行配合 proxy-guard + v2rayN 的正向代理（见 [01-背景与结论.md](./01-背景与结论.md)）；`scripts\set-relay-env.ps1` / `start-openworker-cn.ps1` 属于 v1 遗留脚本，仅在这种调试场景下还有用。
