# 07 · 多用户与用量统计

> 本文是 v2（多用户版）的运维手册：讲解名册模型、从 v1 升级上线的迁移顺序、日常登记/吊销同事 key、用量表记录了什么、怎么查报表。首次把中转从单人版（v1，可选 `RELAY_TOKEN`）切换到公司 10 人版时通读本文；日常只需要查「日常管理」和「查询用量」两节。同事侧不需要读本文——他们的全部操作见最后一节「同事侧体验」。注意：v2 已彻底删除 `RELAY_TOKEN` 机制（v1 时代的可选加固），[03-Worker部署指南.md](./03-Worker部署指南.md) 的「准入控制：KV 名册」一节记录了这段历史，准入控制现在由名册承担。

## 名册模型

身份和准入都来自 Cloudflare KV 里的一份名册（binding 名 `ROSTER`，见 `worker/wrangler.jsonc`）：

- **KV key**：`k:<sha256(api_key) 的 64 位十六进制>`。
- **KV value**：该 key 主人的邮箱纯文本。
- **KV metadata**：`{"email":"...","added":"yyyy-MM-dd"}`（UTC 日期），供 `roster.ps1 -List` 显示，不参与鉴权。

Worker 收到请求后对 `x-goog-api-key` 头做 SHA-256，去 KV 查 `k:<hash>`：查到就得到邮箱（写进用量记录），查不到直接返回 403 `unregistered key`（`worker/src/index.ts`）。KV 读取带 `cacheTtl: 300`，即名册变更在边缘节点最多滞后 5 分钟生效。

为什么是服务端名册、而不是让客户端自己报邮箱：客户端自报的身份头可以随意伪造，记出来的账没有归因价值——LiteLLM 的文档就明确指出自报 `user` 字段 spoofable，其权威记账用的是服务端 virtual-key 绑定，本设计沿用同一惯例。另外「配置只填 key」的需求也让客户端无处取得邮箱，key↔人 的映射本来就在管理员手里，放服务端是唯一自洽的位置。

## 上线迁移顺序

以下全部是管理员在本机的一次性操作，顺序敏感。所有 `npx wrangler` 命令都在 `gemini-relay\worker` 目录下执行，且和 [03-Worker部署指南.md](./03-Worker部署指南.md) 一样要先清掉本会话的代理环境变量（`roster.ps1` 内部会自己清，手工命令要自己清）：

```powershell
cd gemini-relay\worker
Remove-Item Env:HTTP_PROXY, Env:HTTPS_PROXY, Env:ALL_PROXY -ErrorAction SilentlyContinue
```

1. 创建 KV 命名空间，把输出的 id 填进 `wrangler.jsonc` 的 `kv_namespaces[0].id`（替换掉 `TODO-run-wrangler-kv-namespace-create` 占位符）：

   ```powershell
   npx wrangler kv namespace create ROSTER
   ```

2. 创建 D1 数据库，把输出的 `database_id` 填进 `wrangler.jsonc` 的 `d1_databases[0].database_id`（替换掉 `TODO-run-wrangler-d1-create` 占位符）：

   ```powershell
   npx wrangler d1 create gemini_relay_usage
   ```

3. 应用建表迁移（schema 见 `worker/migrations/0001_init.sql`，迁移目录已在 `wrangler.jsonc` 里配置为 `migrations`）：

   ```powershell
   npx wrangler d1 migrations apply gemini_relay_usage --remote
   ```

4. 部署 v2 Worker：

   ```powershell
   npx wrangler deploy
   ```

   **注意：从这条命令生效的那一刻起，所有未登记的 key 立即被 403**，包括管理员自己正在用的那个。所以下一步要马上做。

5. 登记自己的邮箱和 key（key 会安全提示输入，不回显）。仍在 `gemini-relay\worker` 目录下执行：

   ```powershell
   .\..\scripts\roster.ps1 -Add admin@example.com
   ```

6. 跑冒烟测试验证端到端可用。下一条命令的路径是仓库根相对路径，所以先切回仓库根目录，再运行 `test_relay.py`。`scripts/test_relay.py` 的 `resolve_api_key()` 依次尝试环境变量 `GEMINI_API_KEY` → 环境变量 `GOOGLE_API_KEY` → 仓库根 `.env` 的 `GEMINI_API_KEY=` 一行，命中就用——**这个 key 必须已经在名册里**（也就是上一步登记的那个），否则测试只会得到 403。留意顺序：如果本机残留了这两个环境变量中的任意一个，它会悄悄盖过 `.env`，实际测的是另一个（未登记的）key；跑之前建议清掉这两个环境变量，或者确认它们指向的 key 也已登记：

   ```powershell
   cd ..\..
   & "C:\Users\liude\AppData\Local\hermes\hermes-agent\venv\Scripts\python.exe" gemini-relay\scripts\test_relay.py
   ```

7. 逐个登记约 10 位同事（每人一条 `roster.ps1 -Add <邮箱>`，输入各自的 Gemini API key）。

8. 构建并分发 openworker 应用。同事拿到应用后只需要填自己的 API key，见「同事侧体验」。

## 日常管理

`scripts/roster.ps1` 是名册的唯一日常工具，可以在任意目录下运行（内部自动切到 `gemini-relay/worker` 执行 wrangler）。前提：PowerShell 7+，且在 `gemini-relay/worker` 下 `npx wrangler login` 过一次。

登记新人：

```powershell
.\gemini-relay\scripts\roster.ps1 -Add alice@example.com
# 随后按提示安全输入她的 Gemini API key（不回显、不进历史；只有 SHA-256 哈希离开本机）
```

查看名册（邮箱、哈希前 12 位、添加日期）：

```powershell
.\gemini-relay\scripts\roster.ps1 -List
```

吊销（离职/收回访问）：

```powershell
.\gemini-relay\scripts\roster.ps1 -Remove alice@example.com
# 脚本先列出该邮箱名下全部条目，确认后逐条删除；加 -Force 跳过确认
```

两个注意点：

- **吊销有最多 5 分钟的滞后**。Worker 查名册带 `cacheTtl: 300`（`worker/src/index.ts`），被删的 key 在边缘缓存过期前仍可能被放行。对 10 人内部场景这个窗口可接受；如果某次吊销要求即时生效，目前没有比等 5 分钟更快的机制。
- **key 轮换 = 先 `-Remove` 再 `-Add`**。`-Remove` 按邮箱删除该邮箱名下**全部**条目，所以顺序必须是先删旧、后加新——如果先加新 key 再 `-Remove`，新条目会被一并删掉。轮换过程中该同事会有一小段（删除后到登记完成，外加上面的缓存窗口）不可用，提前打个招呼即可。

排错技巧：同事反馈「Test 不通过 / 一直 403」时，先 `roster.ps1 -List` 确认他的邮箱在册；再到用量表里查 `email = '(unregistered)'` 的行，其 `key_hash` 列（12 位哈希前缀）能确认请求确实到达了 Worker、以及用的是哪个 key——登记完成后这个前缀应与 `-List` 显示的前缀一致。

## 用量记录了什么

通过路径白名单校验的请求（包括被 401/403 拒绝的）都会异步写一行到 D1 的 `usage` 表（schema：`worker/migrations/0001_init.sql`；写入逻辑：`worker/src/index.ts` 的 `recordUsage`/`recordRejected`，走 `ctx.waitUntil`，不影响已返回的响应）。未通过白名单的路径从不写入 D1：`/`、`/healthz` 直接返回固定文本，以及不匹配 `ALLOWED_PATH`（扫描器探测、拼写错误）的 404 请求，两者都在分类/记录逻辑之前就返回，不落一行：

| 列 | 含义 |
| --- | --- |
| `id` | 自增主键 |
| `ts` | 请求时间，ISO 8601 UTC |
| `email` | 名册解析出的邮箱；被拒请求为 `(unregistered)` 或 `(no-key)` |
| `model` | 从路径 `/models/{model}:{method}` 提取的模型名（列表/文件类请求为空） |
| `kind` | 请求类型：`generate`\|`stream`\|`embed`\|`count`\|`models`\|`files`\|`other` |
| `status` | 返回给客户端的 HTTP 状态码 |
| `key_hash` | key 的 SHA-256 前 12 位十六进制（识别用，不可逆推出 key） |
| `model_version` | 响应回显的 `modelVersion`（实际服务的模型版本） |
| `response_id` | 响应回显的 `responseId` |
| `prompt_tokens` | 输入 token 数（`promptTokenCount`，含缓存命中部分） |
| `output_tokens` | 输出 token 数（`candidatesTokenCount`） |
| `total_tokens` | 总 token 数（`totalTokenCount`；`countTokens` 请求映射顶层 `totalTokens`） |
| `cached_tokens` | 缓存命中 token 数（`cachedContentTokenCount`） |
| `thoughts_tokens` | 思考 token 数（`thoughtsTokenCount`） |
| `tool_prompt_tokens` | 工具调用提示 token 数（`toolUsePromptTokenCount`） |
| `latency_ms` | 请求进入到上游响应头到达的耗时 |
| `duration_ms` | 到记录侧把响应流完整消费完的总耗时（流式请求近似等于整次生成时长） |
| `error` | `''`（正常）\|`no-key`\|`unregistered`\|`parse-fail`（用量解析失败，token 列为 0 但请求本身有记录） |

流式（SSE）响应的 token 数取的是最后一个 `usageMetadata`——Gemini 的 usageMetadata 是逐 chunk 累计值，最后一次即总量（`worker/src/index.ts` 的 `parseSSE`）。

**明确不记录的内容**：请求体、响应正文（提示词和模型输出永远不落盘）、完整的 API key（KV 里只有哈希，D1 里只有 12 位哈希前缀）。**邮箱是这套系统里唯一的 PII**。

口径说明：这份表统计的是「经中转的 token 数」，供团队内部按人归因；权威计费口径以 Google 侧（AI Studio / Cloud 控制台按项目或按 key 查看）为准，两边不保证逐位对齐（失败请求、部分工具调用场景 Google 的计费口径可能不同）。

## 查询用量

两条路，取其一即可。

**路一：`scripts/usage_report.py`**（本机跑，走 Cloudflare D1 HTTP Query API，不需要 wrangler 也不需要登录控制台）。先设三个环境变量：

```powershell
$env:CF_API_TOKEN = "<Cloudflare API Token，只需 Account/D1/Read 权限>"
$env:CF_ACCOUNT_ID = "<账号 ID，32 位十六进制>"
$env:CF_D1_DATABASE_ID = "<D1 数据库 UUID，npx wrangler d1 info gemini_relay_usage 可查>"
```

API Token 的创建步骤和三个变量的获取位置，`usage_report.py` 顶部文档字符串写得很全。然后用仓库自带的 .venv 解释器跑：

```powershell
# 最近 30 天（默认），每人一行
C:\Users\liude\github\openworker\.venv\Scripts\python.exe gemini-relay\scripts\usage_report.py

# 最近 7 天
C:\Users\liude\github\openworker\.venv\Scripts\python.exe gemini-relay\scripts\usage_report.py --days 7

# 2026 年 8 月整月，附带按模型分解，并导出 CSV
C:\Users\liude\github\openworker\.venv\Scripts\python.exe gemini-relay\scripts\usage_report.py --month 2026-08 --by-model --csv usage-2026-08.csv
```

**路二：Cloudflare 控制台直接跑 SQL**。入口（写作时）：Workers & Pages → D1 → gemini_relay_usage → Console。三条现成语句（口径与脚本一致）：

```sql
-- 1) 本月每人汇总
SELECT
  email,
  COUNT(*) AS requests,
  SUM(prompt_tokens) AS prompt_tokens,
  SUM(output_tokens) AS output_tokens,
  SUM(total_tokens) AS total_tokens,
  SUM(thoughts_tokens) AS thoughts_tokens,
  SUM(CASE WHEN status >= 400 THEN 1 ELSE 0 END) AS failed
FROM usage
WHERE substr(ts, 1, 7) = strftime('%Y-%m', 'now')
GROUP BY email
ORDER BY total_tokens DESC;
```

```sql
-- 2) 每日趋势（最近 30 天）
SELECT
  substr(ts, 1, 10) AS day,
  COUNT(*) AS requests,
  SUM(total_tokens) AS total_tokens
FROM usage
WHERE ts >= datetime('now', '-30 days')
GROUP BY day
ORDER BY day;
```

```sql
-- 3) 按模型分解（本月，每人每模型一行）
SELECT
  email,
  model,
  COUNT(*) AS requests,
  SUM(total_tokens) AS total_tokens
FROM usage
WHERE substr(ts, 1, 7) = strftime('%Y-%m', 'now')
GROUP BY email, model
ORDER BY email ASC, total_tokens DESC;
```

## 额度与保留

按 2026-08 调研时的 Cloudflare 官方文档（数值可能随定价页更新，未在代码中体现，以官方文档为准）：D1 免费计划每天 10 万行写入、500 万行读取、总存储 5 GB。本场景下每个请求写 1 行，10 人即便每人每天 500 次调用也只有 5,000 行/天，写入额度用掉 5%；一行流水只有几百字节，5 GB 够存以千万行计的记录——**按这个量级，流水可以永久保留，不需要任何清理策略**。D1 本身也没有强制保留期，数据不会自动过期。

为什么选 D1 而不是 Workers Analytics Engine（两者都免费可用）：AE 的数据只保留 90 天、没有第一方查询界面（要自己拿 SQL API 拉）、查询结果是采样加权的近似值；D1 数据永久保留、控制台自带 SQL Console、行数和 token 数都是精确值。10 人规模的内部记账，管理体验和精确性都是 D1 完胜，行业惯例（LiteLLM）同样用关系表记账。

顺带一句事实更正：此前阶段的文档结论称「AI Gateway 自定义域名必须配 Cloudflare Access」——按 2026-08 的 Cloudflare 文档，Access 现在是可选项，这条理由已不成立。但仍然不用 AI Gateway 的理由不变：免费计划日志总量上限 10 万条（总量上限，打满即停，不是每日重置）、其路径是 provider 专属前缀形状（与 google-genai SDK 期望的原生路径不一致）、BYOK 模式需要把 API key 托管给 Cloudflare。自建 Worker 三者皆无。

## 同事侧体验

同事视角的全部流程，安装后只有一步：

1. 安装分发的 openworker 应用。
2. 在模型配置里选 Gemini，填入自己的 Gemini API key（形如 `AIza…`，此处用 `<YOUR_GEMINI_API_KEY>` 指代）。就这一个字段，没有任何 URL、token 或代理要配（`coworker/providers/registry.py` 的 gemini 描述符只有 `api_key` 一个字段）。
3. 点 Test。Test 按钮会带着这个 key 请求中转的 `/v1beta/models`（`coworker/providers/registry.py` 的 `verify_provider_key`）：
   - key 已登记 → 通过。
   - key 未登记（管理员还没 `-Add`），或者 key 输入错误/本身无效（这类 key 本来就不可能出现在名册里）→ 中转在把请求转发给 Google 之前就用名册查表拦下，返回 403，提示 "This key is not registered with the company relay yet — ask the admin to add it."。这两种情况从用户视角无法区分；确认确实是有效 key 之后，找管理员登记，登记后重试（注意边缘缓存，最多等 5 分钟）。
   - key 已登记，但 Google 侧已吊销/停用 → 中转正常放行、把请求转发到 Google，由 Google 上游返回错误，Test 同样不通过，但这时看到的是 Google 返回的错误而不是"未登记"提示。

不需要 VPN：客户端默认直连 `https://gemini.smjtools.com`（`coworker/providers/gemini_provider.py` 的 `RELAY_BASE_URL`），这是 Cloudflare 自定义域名；部署后本机已实测连通（`test_relay.py` 非流式 + 流式双 PASS，见 [05-验证与排错.md](./05-验证与排错.md)），但"大陆各网络环境下都可达"仍非保证，同事侧首次使用建议先点一次 Test 确认健康；`workers.dev` 域名已在 `wrangler.jsonc` 里禁用。**中转不可用时没有回退**——设计如此：与其静默改连大陆不可达的 Google 原始域名，不如直接报错。调试通道（环境变量 `GOOGLE_GEMINI_BASE_URL`、profile 隐藏键 `base_url`，优先级：profile 显式值 > 环境变量 > 中转，见 `resolve_base_url`）只给管理员排障用，不向同事说明。
