# 07 · 多用户与用量统计

> 本文是多用户版的运维手册：讲解名单模型、迁移上线顺序、日常加人/删人、用量表记录了什么、怎么查报表。首次上线或做版本迁移时通读本文；日常只需要查「日常管理」和「查询用量」两节。同事侧不需要读本文——他们的全部操作见最后一节「同事侧体验」。
>
> **v3 变更**：身份不再来自「同事各自的 Gemini API key 的哈希」，而来自 **Cloudflare Access 一次性验证码登录**。登录只解决「你是谁」——调 Google 用的是**每人一把、由管理员从一个公司 Google 账号签发并以他名字命名**的 key，中转原样转发、一把都不存。这两件事拆开，才能按验证过的邮箱做**限额闸门**（换 key 重置不了计数器），同时在 Google 侧也保留一本按人的账。Access 侧的一次性配置见 [08-Access登录配置.md](./08-Access登录配置.md)。历史沿革：v1 有个可选的 `RELAY_TOKEN` 加固，v2 删掉它换成 key 哈希名册（见 [03-Worker部署指南.md](./03-Worker部署指南.md)），v3 换成登录令牌 + 一人一把命名 key + 按人限额。

## 名单与令牌模型

一个 KV 命名空间（binding 名 `ROSTER`，见 `worker/wrangler.jsonc`）装四类记录，靠 key 前缀区分：

| 前缀 | 内容 | 生命周期 |
| --- | --- | --- |
| `u:<邮箱>` | 名单条目。value 是 `{"name","dept","role","added"}` 的 JSON（Worker 读它）；metadata 存同样字段，供 `roster.ps1 -List` 一次列全而不用逐条 GET | 由 `roster.ps1` 增删，无过期 |
| `t:<sha256(令牌)>` | 登录令牌 → 邮箱 | 30 天 TTL |
| `s:<sha256(sid)>` | 待完成的登录会话（回调地址 + PKCE challenge） | 10 分钟 TTL，用一次即删 |
| `c:<sha256(code)>` | 一次性授权码（邮箱 + PKCE challenge） | 5 分钟 TTL，用一次即删 |

**两道闸，各管一段。** Access 策略里的邮箱列表决定谁能收到验证码、谁能过登录页；KV 名单决定谁能换到令牌、谁的令牌还算数。加人删人两边都要动，对照表见 [08-Access登录配置.md](./08-Access登录配置.md) 的「名单变更」一节。

**准入怎么做的**：Worker 从 `Authorization: Bearer` 或 `x-goog-api-key` 里取出令牌（google-genai SDK 走后者——应用把令牌存在 SDK 眼中的 `api_key` 位置），查 `t:<sha256(令牌)>` 得到邮箱，再查 `u:<邮箱>` 确认这个人还在名单里。两次 KV 读都带 `cacheTtl: 300`，所以名单变更在边缘最多滞后 5 分钟生效。**令牌记录里只存邮箱、不存姓名部门**，正是为了让「删掉一条 `u:` 记录」就能吊销这个人手上所有设备的所有令牌，不必去枚举它们。

为什么是服务端签发的令牌、而不是让客户端自己报邮箱：客户端自报的身份头可以随意伪造，记出来的账没有归因价值——LiteLLM 的文档就明确指出自报 `user` 字段 spoofable，其权威记账用的是服务端 virtual-key 绑定，本设计沿用同一惯例。v2 用 key 哈希达到同样效果；v3 的登录令牌更进一步：邮箱不再是管理员手工登记的一条映射，而是同事自己通过 Cloudflare 验证码**证明**出来的。

## 上线迁移顺序

以下全部是管理员在本机的一次性操作，顺序敏感。所有 `npx wrangler` 命令都在 `gemini-relay\worker` 目录下执行，且和 [03-Worker部署指南.md](./03-Worker部署指南.md) 一样要先清掉本会话的代理环境变量（`roster.ps1` 内部会自己清，手工命令要自己清）：

```powershell
cd gemini-relay\worker
Remove-Item Env:HTTP_PROXY, Env:HTTPS_PROXY, Env:ALL_PROXY -ErrorAction SilentlyContinue
```

1. 创建 KV 命名空间，把输出的 id 填进 `wrangler.jsonc` 的 `kv_namespaces[0].id`（替换掉 `TODO-run-wrangler-kv-namespace-create` 占位符）：

   ```powershell
   npx wrangler kv namespace create ROSTER
   ```

2. 创建 D1 数据库，把输出的 `database_id` 填进 `wrangler.jsonc` 的 `d1_databases[0].database_id`（替换掉 `TODO-run-wrangler-d1-create` 占位符）：

   ```powershell
   npx wrangler d1 create gemini_relay_usage
   ```

3. 应用建表迁移。`worker/migrations/` 下的文件按序号依次执行，三个迁移建出三张表——`0001_init.sql` 建 `usage`（用量流水），`0002_login.sql` 给 `usage` 补 `name`/`dept` 两列并建 `auth_events`（登录审计），`0003_quota.sql` 建 `quota`（限额计数器）。迁移目录已在 `wrangler.jsonc` 里配置为 `migrations`，一条命令全部应用：

   ```powershell
   npx wrangler d1 migrations apply gemini_relay_usage --remote
   ```

4. 定限额默认值。这一步没有机密要放——**这个 Worker 一个 `wrangler secret` 都没有**。改
   `worker/wrangler.jsonc` 里 `vars` 的 `QUOTA_RPM` / `QUOTA_RPD` / `QUOTA_TPD` 即可（默认
   30 / 1200 / 5000000）。要给某个人开小灶就写进名单 CSV 的 `rpm,rpd,tpd` 三列。

5. 按 [08-Access登录配置.md](./08-Access登录配置.md) 配好 Zero Trust（One-time PIN、只保护 `/login` 的 Access 应用、允许名单策略），并把 `ACCESS_TEAM_DOMAIN` / `ACCESS_AUD` 填进 `wrangler.jsonc`。**必须在部署前完成**，否则登录路径拿不到 Access 断言，一律 403。

6. 部署 Worker：

   ```powershell
   npm install
   npx wrangler deploy
   ```

   **注意：从这条命令生效的那一刻起，所有没有登录令牌的请求立即被 401**，包括管理员自己正在用的那个 v2 API key。所以下一步要马上做。`deploy` 还会一并注册每天清理限额计数桶的定时任务（`triggers.crons`），不用另外配。

7. 登记名单（含自己）。真实名单在 `gemini-relay\scripts\roster.csv`，四列必填 `email,name,dept,role` 加三列选填 `rpm,rpd,tpd`（留空=用 Worker 默认值，`-1`=不限，`0`=停用）；这个文件不进 git（本仓库是公开 fork），仓库里只有占位用的 `roster.example.csv`：

   ```powershell
   cd ..\..
   .\gemini-relay\scripts\roster.ps1 -Import
   .\gemini-relay\scripts\roster.ps1 -AccessList   # 把打印出来的邮箱贴进 Access 策略
   ```

8. 在 openworker 里走一遍真登录：**设置 ▸ 模型 ▸ Gemini ▸ 登录**。

9. 跑冒烟测试验证端到端可用。下一条命令的路径是仓库根相对路径，所以先切回仓库根目录，再运行 `test_relay.py`。它自己会把两个凭证找齐（登录令牌从上一步登录后的 secret store 里读，Gemini key 从环境变量/secret store/`.env` 里读），开头会打印各自来源和当天的限额读数：

   ```powershell
   cd ..\..
   & "C:\Users\liude\AppData\Local\hermes\hermes-agent\venv\Scripts\python.exe" gemini-relay\scripts\test_relay.py
   ```

10. 构建并分发 openworker 应用。同事拿到应用后只需要点一次「登录」，见「同事侧体验」。

## 日常管理

`scripts/roster.ps1` 是名单的唯一日常工具，可以在任意目录下运行（内部自动切到 `gemini-relay/worker` 执行 wrangler）。前提：PowerShell 7+，且在 `gemini-relay/worker` 下 `npx wrangler login` 过一次。**它不再需要任何人的 API key**。

加人（改 CSV 后重跑 `-Import` 是幂等的，已有的人会被更新成 CSV 里的最新姓名/部门/角色）：

```powershell
.\gemini-relay\scripts\roster.ps1 -Import
# 或者单独加一个：
.\gemini-relay\scripts\roster.ps1 -Add alice@example.com -Name 张三 -Dept 技术研发部 -Role lead
```

查看名单（邮箱、姓名、部门、角色、登记日期，外加当前活跃令牌数）：

```powershell
.\gemini-relay\scripts\roster.ps1 -List
```

打印该贴进 Access 策略的邮箱列表：

```powershell
.\gemini-relay\scripts\roster.ps1 -AccessList
```

删人（离职/收回访问）：

```powershell
.\gemini-relay\scripts\roster.ps1 -Remove alice@example.com
# 加 -Force 跳过确认
```

三个注意点：

- **删人要两边都做**。`-Remove` 删的是 KV 名单，他名下所有设备上的令牌随之失效；但 Access 策略里的邮箱要另外去控制台删掉，否则他仍然收得到验证码、过得了登录页（只是换不到令牌）。脚本每次都会提醒。
- **生效有最多 5 分钟的滞后**。Worker 查名单带 `cacheTtl: 300`（`worker/src/auth.ts`），被删的人在边缘缓存过期前仍可能被放行。对十来人的内部场景这个窗口可接受；如果某次收回要求即时生效，目前没有比等 5 分钟更快的机制。
- **key 轮换是各人自己的事**。中转不持有任何 key，也就没有需要你去轮换的凭证。谁的 key 泄露了，他自己去 Google 后台换一把再填进 OpenWorker，别人完全不受影响。令牌那边 30 天自动过期，重新登录即可。
- **调额度和停用只动名单一边**。`-Add <同一个邮箱> -Rpd 3000` 就是覆盖（重复登记是幂等的），`-Rpd 0` 是停用——人留在名单和 Access 策略里，但所有请求 429。比删人可逆得多，适合「先停一下看看怎么回事」。改完最长 5 分钟生效（同样是那个 KV 边缘缓存）。

排错技巧：同事反馈「一直 401/403」时，先 `roster.ps1 -List` 确认他的邮箱在名单里；再到用量表里查 `email` 为 `(no-token)`（压根没带令牌，通常是没登录）或 `(revoked)`（令牌过期/被吊销/人已不在名单）的行——`key_hash` 列（令牌哈希前 12 位）能确认请求确实到达了 Worker。登录本身的成败在 `auth_events` 表里，见下一节。

## 限额闸门怎么看

闸门的计数器在同一个 D1 库的 `quota` 表里（`worker/migrations/0003_quota.sql`），和 `usage`
流水表回答的问题不一样：`usage` 是流水账，问「这个月谁用了多少」；`quota` 是当下的闸门读数，
问「谁今天快撞墙了」。分钟桶三天后被定时任务清掉，所以 `quota` 只能看今天，历史一律查 `usage`。

看全员当天读数：

```powershell
& "C:\Users\liude\github\openworker\.venv\Scripts\python.exe" `
    gemini-relay\scripts\usage_report.py --days 1 --by-dept --quota
```

`--quota` 那张表里 `peak_per_min` 是今天最忙的那一分钟打了多少次——比「此刻是多少」有用得多，
一次跑飞的循环会在这一列上很明显。上限本身不在这张表里：每个人的上限看 `roster.ps1 -List` 的
`Limits` 列（显示「默认/不限/停用/具体数字」），没设的取 `wrangler.jsonc` 的 `QUOTA_*`。

同事自己也能看到：设置 ▸ 模型 ▸ Gemini 的登录卡片上有一行「今日 12/1200 次请求 · 34k/5M
tokens」，用到 90% 会变红。这是有意的——不想让人撞了墙才知道有墙。

被闸门拒掉的请求会在 `usage` 表里留下一行 `status=429`、`error` 形如 `quota-rpd` 的记录，所以
「某人今天被拦了多少次、拦在哪一档」也能事后查：

```sql
SELECT email, error, COUNT(*) AS blocked
FROM usage
WHERE status = 429 AND ts >= datetime('now', '-7 days')
GROUP BY email, error
ORDER BY blocked DESC;
```

被拒的请求本身**不计入**计数器——让 429 再消耗额度会变成自我强化的死循环。

## 用量记录了什么

通过路径白名单校验的请求（包括被 401/403 拒绝的）都会异步写一行到 D1 的 `usage` 表（建表在 `worker/migrations/0001_init.sql`，`name`/`dept` 两列是 `0002_login.sql` 后加的，下表列的是两个迁移都跑完之后的现状；写入逻辑：`worker/src/index.ts` 的 `recordUsage`/`recordRejected`，走 `ctx.waitUntil`，不影响已返回的响应）。未通过白名单的路径从不写入 D1：`/`、`/healthz` 直接返回固定文本，以及不匹配 `ALLOWED_PATH`（扫描器探测、拼写错误）的 404 请求，两者都在分类/记录逻辑之前就返回，不落一行：

| 列 | 含义 |
| --- | --- |
| `id` | 自增主键 |
| `ts` | 请求时间，ISO 8601 UTC |
| `email` | 令牌解析出的邮箱；被拒请求为 `(no-token)`（没带令牌）或 `(revoked)`（令牌过期/被吊销/人已不在名单） |
| `name` | 请求发生时该邮箱在名单里的姓名（被拒请求为空） |
| `dept` | 请求发生时该邮箱在名单里的部门（被拒请求为空） |
| `model` | 从路径 `/models/{model}:{method}` 提取的模型名（列表/文件类请求为空） |
| `kind` | 请求类型：`generate`\|`stream`\|`embed`\|`count`\|`models`\|`files`\|`other` |
| `status` | 返回给客户端的 HTTP 状态码 |
| `key_hash` | 登录令牌的 SHA-256 前 12 位十六进制（识别用，不可逆推出令牌）。列名沿用 v2，含义在 `0002_login.sql` 之后变成了令牌哈希——迁移前写的行仍是旧含义（当时各人 API key 的哈希） |
| `model_version` | 响应回显的 `modelVersion`（实际服务的模型版本） |
| `response_id` | 响应回显的 `responseId` |
| `prompt_tokens` | 输入 token 数（`promptTokenCount`，含缓存命中部分） |
| `output_tokens` | 输出 token 数（`candidatesTokenCount`） |
| `total_tokens` | 总 token 数（`totalTokenCount`；`countTokens` 请求映射顶层 `totalTokens`） |
| `cached_tokens` | 缓存命中 token 数（`cachedContentTokenCount`） |
| `thoughts_tokens` | 思考 token 数（`thoughtsTokenCount`） |
| `tool_prompt_tokens` | 工具调用提示 token 数（`toolUsePromptTokenCount`） |
| `latency_ms` | 请求进入到上游响应头到达的耗时 |
| `duration_ms` | 到记录侧把响应流完整消费完的总耗时（流式请求近似等于整次生成时长） |
| `error` | `''`（正常）\|`no-token`（没登录）\|`bad-token`（令牌失效/已不在名单）\|`no-upstream-key`（登录了但没带自己的 Gemini key）\|`token-as-key`（旧版客户端把令牌塞在 key 的位置）\|`quota-rpm`/`quota-rpd`/`quota-tpd`/`quota-suspended`（撞限额闸门，429）\|`parse-fail`（用量解析失败，token 列为 0 但请求本身有记录） |

流式（SSE）响应的 token 数取的是最后一个 `usageMetadata`——Gemini 的 usageMetadata 是逐 chunk 累计值，最后一次即总量（`worker/src/index.ts` 的 `parseSSE`）。

`name` / `dept` 是**请求发生那一刻的快照**，不是外键。有人换了部门，历史用量仍然挂在当时那个部门下——按月出账时这正是想要的口径。

上面那张表是按可读性排的（身份相关的列排在一起）。**库里的物理列序不是这个**：`name` / `dept` 是 `0002_login.sql` 用 `ALTER TABLE ADD COLUMN` 追加的，SQLite 一律把新列加在末尾，所以 `SELECT *` 取出来的顺序是 `id, ts, email, model, …, duration_ms, error, name, dept`。写查询时按列名取，别依赖位置。

**登录本身记在另一张表 `auth_events`**（`worker/migrations/0002_login.sql`，写入逻辑在 `worker/src/auth.ts`）：`ts`、`email`、`event`（`login-ok`\|`login-denied`\|`token-issued`\|`token-denied`\|`logout`）、`detail`（如 `not in roster`、`pkce mismatch`）、`country`（Access 看到的登录来源国家）。和用量分开是因为它是安全证据而不是账单数据——问的问题不同、保留需求不同，而且一次「登录了但一条请求都没发」也必须留下痕迹。排查登录问题先看这张表：

```sql
SELECT ts, email, event, detail, country FROM auth_events ORDER BY ts DESC LIMIT 50;
```

**明确不记录的内容**：请求体、响应正文（提示词和模型输出永远不落盘）、完整的 API key（KV 里只有哈希，D1 里只有 12 位哈希前缀）。**邮箱是这套系统里唯一的 PII**。

口径说明：这份表统计的是「经中转的 token 数」，供团队内部按人归因；权威计费口径以 Google 侧（AI Studio / Cloud 控制台按项目或按 key 查看）为准，两边不保证逐位对齐（失败请求、部分工具调用场景 Google 的计费口径可能不同）。

## 查询用量

两条路，取其一即可。

**路一：`scripts/usage_report.py`**（本机跑，走 Cloudflare D1 HTTP Query API，不需要 wrangler 也不需要登录控制台）。先设三个环境变量：

```powershell
$env:CF_API_TOKEN = "<Cloudflare API Token，只需 Account/D1/Read 权限>"
$env:CF_ACCOUNT_ID = "<账号 ID，32 位十六进制>"
$env:CF_D1_DATABASE_ID = "<D1 数据库 UUID，npx wrangler d1 info gemini_relay_usage 可查>"
```

API Token 的创建步骤和三个变量的获取位置，`usage_report.py` 顶部文档字符串写得很全。然后用仓库自带的 .venv 解释器跑：

```powershell
# 最近 30 天（默认），每人一行
C:\Users\liude\github\openworker\.venv\Scripts\python.exe gemini-relay\scripts\usage_report.py

# 最近 7 天
C:\Users\liude\github\openworker\.venv\Scripts\python.exe gemini-relay\scripts\usage_report.py --days 7

# 2026 年 8 月整月，附带按模型分解，并导出 CSV
C:\Users\liude\github\openworker\.venv\Scripts\python.exe gemini-relay\scripts\usage_report.py --month 2026-08 --by-model --csv usage-2026-08.csv
```

**路二：Cloudflare 控制台直接跑 SQL**。入口（写作时）：Workers & Pages → D1 → gemini_relay_usage → Console。三条现成语句（口径与脚本一致）：

```sql
-- 1) 本月每人汇总
SELECT
  email,
  COUNT(*) AS requests,
  SUM(prompt_tokens) AS prompt_tokens,
  SUM(output_tokens) AS output_tokens,
  SUM(total_tokens) AS total_tokens,
  SUM(thoughts_tokens) AS thoughts_tokens,
  SUM(CASE WHEN status >= 400 THEN 1 ELSE 0 END) AS failed
FROM usage
WHERE substr(ts, 1, 7) = strftime('%Y-%m', 'now')
GROUP BY email
ORDER BY total_tokens DESC;
```

```sql
-- 2) 每日趋势（最近 30 天）
SELECT
  substr(ts, 1, 10) AS day,
  COUNT(*) AS requests,
  SUM(total_tokens) AS total_tokens
FROM usage
WHERE ts >= datetime('now', '-30 days')
GROUP BY day
ORDER BY day;
```

```sql
-- 3) 按模型分解（本月，每人每模型一行）
SELECT
  email,
  model,
  COUNT(*) AS requests,
  SUM(total_tokens) AS total_tokens
FROM usage
WHERE substr(ts, 1, 7) = strftime('%Y-%m', 'now')
GROUP BY email, model
ORDER BY email ASC, total_tokens DESC;
```

```sql
-- 4) 按部门汇总（本月）—— v3 新增 dept 列之后才可用
SELECT
  CASE WHEN dept = '' THEN '(未挂部门)' ELSE dept END AS dept,
  COUNT(DISTINCT email) AS people,
  COUNT(*) AS requests,
  SUM(total_tokens) AS total_tokens
FROM usage
WHERE substr(ts, 1, 7) = strftime('%Y-%m', 'now') AND status < 400
GROUP BY dept
ORDER BY total_tokens DESC;
```

## 额度与保留

按 2026-08 调研时的 Cloudflare 官方文档（数值可能随定价页更新，未在代码中体现，以官方文档为准）：D1 免费计划每天 10 万行写入、500 万行读取、总存储 5 GB。本场景下每个请求写 1 行，10 人即便每人每天 500 次调用也只有 5,000 行/天，写入额度用掉 5%；一行流水只有几百字节，5 GB 够存以千万行计的记录——**按这个量级，流水可以永久保留，不需要任何清理策略**。D1 本身也没有强制保留期，数据不会自动过期。

为什么选 D1 而不是 Workers Analytics Engine（两者都免费可用）：AE 的数据只保留 90 天、没有第一方查询界面（要自己拿 SQL API 拉）、查询结果是采样加权的近似值；D1 数据永久保留、控制台自带 SQL Console、行数和 token 数都是精确值。10 人规模的内部记账，管理体验和精确性都是 D1 完胜，行业惯例（LiteLLM）同样用关系表记账。

顺带一句事实更正：此前阶段的文档结论称「AI Gateway 自定义域名必须配 Cloudflare Access」——按 2026-08 的 Cloudflare 文档，Access 现在是可选项，这条理由已不成立。但仍然不用 AI Gateway 的理由不变：免费计划日志总量上限 10 万条（总量上限，打满即停，不是每日重置）、其路径是 provider 专属前缀形状（与 google-genai SDK 期望的原生路径不一致）、BYOK 模式需要把 API key 托管给 Cloudflare。自建 Worker 三者皆无。

## 同事侧体验

同事视角一共两件事：**登录**（你是谁）和**填管理员发给他的 Gemini API key**（去调 Google 的凭证）。两件都做完那一栏才可用。

1. 安装分发的 openworker 应用。
2. 打开 **设置 ▸ 模型 ▸ Gemini**，点「登录」。系统浏览器会自动打开 Cloudflare 的登录页。
3. 在登录页填自己的公司邮箱 → 收验证码（10 分钟有效、只能用一次）→ 填码。
4. 浏览器显示「已登录」卡片，可以关掉；回到 openworker，Gemini 那一栏会显示「✓ 已登录」和自己的姓名/部门。
5. 卡片下方的 API key 输入框里填**管理员发给他的**那把 Gemini key（每人一把、以他名字命名，不用自己申请），点 Test。

第 5 步没做的话，卡片上会有一行红字提示，发第一条消息会收到一条中文的 400 说明缺哪一半。登录成功后卡片上还会显示今天的用量和上限（「今日 12/1200 次请求 · 34k/5M tokens」），用到 90% 变红。

会遇到的几种情况：

- **收不到验证码** → 邮箱不在 Access 策略里（被拒的人**不会**收到邮件，但页面仍然显示「验证码已发送」，Cloudflare 故意不泄露谁在名单里），或者进了垃圾箱。找管理员登记。
- **过了验证码，但提示「这个邮箱不在允许名单里」** → Access 那边加了、KV 名单这边还没加。找管理员跑一次 `roster.ps1 -Import`。
- **验证码说「已被使用」** → 邮箱安全网关替用户先点了链接、把一次性码消费掉了。改成手动输入 6 位码而不是点链接。
- **用着用着提示要重新登录** → 令牌 30 天到期，或者管理员收回了权限。重新点一次「登录」即可；真被收回了会停在上面那条「不在允许名单里」。重新登录**不会**动你自己的 API key，它一直留在本机。
- **提示「今天的额度用满了」** → 撞上限额闸门。文案会写明是每分钟还是每天：每分钟那档等一分钟（一次复杂任务里 agent 循环十几次请求很正常，容易撞）；每天那档等北京时间次日 0 点，或者找管理员调高。

不需要 VPN；需要管理员发的那把 Gemini API key。客户端默认直连 `https://gemini.smjtools.com`（`coworker/providers/gemini_provider.py` 的 `RELAY_BASE_URL`），这是 Cloudflare 自定义域名；部署后本机已实测连通（`test_relay.py` 非流式 + 流式双 PASS，见 [05-验证与排错.md](./05-验证与排错.md)），但"大陆各网络环境下都可达"仍非保证，同事侧首次使用登录能走通就说明链路是通的；`workers.dev` 域名已在 `wrangler.jsonc` 里禁用。**中转不可用时没有回退**——设计如此：与其静默改连大陆不可达的 Google 原始域名，不如直接报错。调试通道（环境变量 `GOOGLE_GEMINI_BASE_URL`、profile 隐藏键 `base_url`，优先级：profile 显式值 > 环境变量 > 中转，见 `resolve_base_url`）只给管理员排障用，不向同事说明。
