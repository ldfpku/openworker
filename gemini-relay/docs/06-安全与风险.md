# 06 - 安全与风险

> 本文是什么：中转方案引入的信任边界、登录与令牌模型、PII 边界、滥用面、平台风险与合规提示的一次性说明。
> 建议在决定长期使用中转（而不只是临时验证）、尤其是分发给同事之前通读一遍。

## 信任边界

中转 Worker 是明文请求的必经之路，能看到全部对话内容——这是反向代理的固有性质，
不是这个方案特有的缺陷。这个前提可接受的**唯一条件**是：域名 `smjtools.com` 与
Worker 都由管理者本人的 Cloudflare 账号控制。**这一条已经确认**：smjtools.com 这个
zone 和 gemini-relay 这个 Worker 都在管理者本人的 Cloudflare 账号下。要清楚地意识到：
中转地址内置在 `gemini_provider.py`（`RELAY_BASE_URL` 常量）里，装了 openworker 的每台
机器上所有 Gemini 请求**默认**发往这台主机；账号归属就是这套方案的地基，换人接手时
第一件要交接的事就是它。

**凭证是两把，各管一件事。** 客户端每个请求同时带：

| 头 | 内容 | 谁消费 |
|---|---|---|
| `Authorization: Bearer owr_...` | 登录令牌，只对本中转有效 | 中转自己，转发前剥掉，Google 看不到 |
| `x-goog-api-key: AIza...` | **调用方自己的** Gemini key | Google，中转原样转发、不改不存 |

这个拆分是有意的，两半各自的安全含义不同：

- **登录令牌**回答「你是谁」。它不是 Google 凭证，泄露的最坏后果是「有人以他的名义用
  中转」——会被记账、会被吊销、会撞上他的限额，而不是「有人拿到一把能直接调 Google 的
  key」。删一条 KV 名单记录就吊销他名下所有设备的令牌。
- **各自的 Gemini key** 回答「谁付钱」。中转**不保存任何人的 key**：没有共享机密、没有
  KV 里的 key 表、没有可以被一次性偷走的集合。key 只是随请求头过一遍。这也意味着一个
  人的 key 泄露只影响他自己，轮换是他自己在 Google 侧的事，不需要惊动别人。

代价要说清楚：中转在转发的那一瞬间**能看到**每个人的 key（反向代理的固有性质，和它能
看到对话内容是同一回事）。真正的边界不是「中转看不看得到」，而是「中转由谁控制」——回到
上面那一条。曾经短暂存在过的共享上游 key（v3 早期的 `GEMINI_API_KEY` 机密）已经删除；
如果某个部署里还留着这个机密，它已经不被读取了，`npx wrangler secret delete
GEMINI_API_KEY` 清掉即可。

Worker 代码本身（[worker/src/index.ts](../worker/src/index.ts)、
[worker/src/auth.ts](../worker/src/auth.ts)）不记录、不持久化任何请求正文或响应正文
——没有一行 `console.log` 输出请求体或敏感头；日志输出只有几处 `console.error`：D1
写入失败、记录支路整体失败（这种情况仍会补记一条 `error='parse-fail'` 的用量行）、
以及 Access 断言校验失败。都只打印错误对象，行内没有请求内容、令牌或 key。Worker 会
把**用量元数据**持久化进 D1（邮箱、姓名、部门、模型名、token 计数、HTTP 状态、令牌的
SHA-256 前 12 位——完整令牌、任何人的 Gemini key 和对话内容永不入库），以及限额计数器
（邮箱 + 时间桶 + 两个整数），边界详见下面的 PII 一节。
`wrangler tail` 只是运维时临时接上的实时流，用完即止，不落盘存储。

## 登录与令牌模型

准入分两道闸，机制不同、失效方式也不同：

1. **Cloudflare Access（One-time PIN）** 守着 `/login`，决定谁能证明自己拥有某个邮箱。
   配置见 [08-Access登录配置.md](./08-Access登录配置.md)。
2. **KV 名单 + 登录令牌** 守着中转本身，决定谁能真正发请求。

这条链路上几个刻意的设计选择：

- **Access 断言要验签，不能只看 header 在不在。** Worker 用 team domain 的 JWKS 验
  RS256 签名并核对 `iss`/`aud`（`worker/src/access.ts`）。这既是 Cloudflare 的官方要求，
  也兜住了配置漂移——万一 Access 应用被删或 Path 被改宽，验签失败会让登录直接 403，
  而不是悄悄退化成一个「谁填什么邮箱都认」的表单。
- **回调只允许回环地址。** `/auth/session` 只接受
  `http://127.0.0.1:<任意端口>/relay/callback`（RFC 8252 §7.3；端口不能固定，桌面端每
  次启动随机绑）。不这么限制，中转就成了一个会往任意地址发授权码的开放重定向器。
- **PKCE 绑定兑换方。** 本机任何进程都能抢先占住那个回环端口；把授权码绑到
  `sha256(verifier)` 上，只有真正发起登录的那个 openworker 进程能兑换。
- **一次性、短命、只存哈希。** 登录会话 10 分钟、授权码 5 分钟且用一次即删；
  `sid`/`code`/令牌在 KV 里全部只存 SHA-256，KV 被读走也换不出可用凭证。
- **关键参数不走 query string。** Access 做路径匹配时不看 query，登录跳转过程中还可能
  改写它，所以参数存在服务端会话里，URL 路径上只有一个不可猜的 `sid`。
- **令牌 30 天过期、按设备发放。** 删掉一条 KV 名单记录就能吊销那个人**所有**设备上
  的所有令牌（令牌记录里只存邮箱，需要回查名单），最多 5 分钟内生效。

登录成败全部记进 D1 的 `auth_events` 表（谁登录、谁被拒、来源国家），和用量分表存放
——它是安全证据，不是账单数据。

## 个人信息（PII）边界

这套系统里的 PII 是**同事的邮箱、姓名和部门**（v2 只有邮箱，v3 为了出部门报表加了
姓名和部门）。它们存在三个地方——KV 名单（`u:` 记录的 value 和 metadata）、D1 `usage`
表的每一行流水、D1 `auth_events` 表的每一条登录记录。要点：

- **真实名单不进仓库**：本仓库是公开 fork，`gemini-relay/scripts/roster.csv` 在
  `.gitignore` 里，只留在管理员本机；仓库里只有占位用的 `roster.example.csv`。同事的
  姓名和私人邮箱一旦提交进公开 git 历史就基本清不掉了，这条不要图省事。
- **保留期是永久**：D1 没有配置任何 TTL 或清理任务，删除名单条目只影响准入，**不会**
  删除该邮箱名下已有的历史用量行和登录记录。想抹掉某人的历史需要手动在 D1 控制台
  执行 DELETE。
- **谁能读到**：Cloudflare 账号的登录者（控制台 KV/D1 界面），以及任何持有带
  Account → D1 → Read 权限 API Token 的人（`usage_report.py` 用的 `CF_API_TOKEN`
  就是这种）。Token 建议按最小权限创建（只给 D1 Read、限定到目标账号），并按
  秘密对待。
- **登录记录多了一个字段**：`auth_events.country` 是 Access 看到的登录来源国家。它是
  粗粒度的（国家级，不是 IP），但仍然是一条位置信息，纳入上面的保留和访问口径。
- **限额计数器只有计数**：`quota` 表每行是「邮箱 + 时间桶 + 请求数 + token 数」，没有
  内容、没有凭证。分钟桶三天后由定时任务删除，日桶同理。
- **除此之外无其他 PII**：流水里没有请求体、响应正文、完整令牌，也没有任何人的 Gemini
  key（中转从不存 key）；令牌只以 SHA-256 前 12 位出现，用于排查，无法还原。
- 在公司内分发前，应让同事知道"经中转的调用会按邮箱记录 token 用量、登录会留痕"这一
  事实（记录内容与查询方式见 [07-多用户与用量统计.md](./07-多用户与用量统计.md)）。

## 滥用面

外部滥用面很小：`gemini.smjtools.com` 即使被发现，外人没有登录令牌就是
`401`；令牌拿不到，因为签发它要先过 Cloudflare 的邮箱验证码，而验证码只发给
Access 策略里的邮箱。最坏情况是消耗 Cloudflare 侧的请求配额、带宽和 D1 写入额度
——被拒绝的请求也会各记一条流水（email 为 `(no-token)`/`(revoked)`），极端的扫描
洪泛理论上能写满 D1 的每日写入额度，但不会泄露账号、令牌或任何人的 Gemini key。

**内部滥用面**：这里曾经有个真缺口——上游 key 共享、Worker 侧没有任何按人的限制，
任何一个人都能把全公司的额度跑光。现在两头都堵上了：每个人用自己的 key，所以跑飞的
代价落在跑飞的那个人自己账上；`quota.ts` 的计数闸按**验证过的邮箱**计数（不是按 key，
所以换一把 key 不会重置计数器），撞上就是 429。

闸门的默认值在 `wrangler.jsonc` 的 `QUOTA_*` 里，每个人可以在名单里用 rpm/rpd/tpd 覆盖，
`-1` 不限、`0` 停用。三档的分工值得说明：

- **rpm（每分钟请求数）是防跑飞的**，不是省钱的。一个失控的工具循环一分钟能打几百次
  请求，这道闸几秒钟内就拦住它。**任何人都不建议关掉它**，包括管理员——真需要跑批量
  任务时临时调高，别设成 `-1`。
- **rpd / tpd（每日请求数、每日 token 数）是治理用的**。既然各付各的，它们更像是一个
  「你今天用得比平常多得多」的提醒，以及一个不必动 Google 账号就能用的总闸。管理员和
  总经理的日上限设成 `-1`（见 `roster.example.csv` 的注释），rpm 保留默认。
- **`0` 是停用开关**：人还在名单里、Access 策略也不用动，但所有请求 429。比删人再加
  回来温和，适合「先停一下看看怎么回事」。

闸门有意做成**读失败即放行**（`readCounters` 吞掉 D1 异常）：它是治理机制不是安全机制，
把谁挡在门外是名单的职责，让一次 D1 抖动变成全公司断线是更糟的失败。事后视角仍然保留：
D1 里按人、按部门、按当日闸门读数的查询见
[07-多用户与用量统计.md](./07-多用户与用量统计.md)。

另一个要留意的点：吊销不是瞬时的。名单查询带 `cacheTtl: 300` 边缘缓存，删除条目后
那个人的令牌在最长 5 分钟内仍可能被放行（离职/设备丢失场景下这 5 分钟窗口要心里
有数）。

缓解手段（按接入成本从低到高）：

- 域名保持低调，不在公开渠道宣传。
- 名单只登记在册同事，人员变动及时 `roster.ps1 -Remove` **并同步删 Access 策略**。
- 定期看一眼 `auth_events`（意料之外的登录来源国家、反复的 `login-denied`）和按人用量
  （某个人的曲线突然翘起来）。
- 在 Cloudflare WAF 加速率限制规则，压制异常高频请求（WAF 按 IP，闸门按人，两者互补）。
- 发现某个人的用量异常，先把他的 rpd 调低或置 0（`roster.ps1 -Add <他的邮箱> ... -Rpd 0`，
  重复登记就是覆盖），再去问情况——这比删人可逆得多。
- 中转没有可轮换的 key。谁的 key 泄露了，谁自己去 Google 后台换一把，再在 OpenWorker 里
  填新的，其他人完全不受影响。

**注意别把安全设置调过头**：zone 上的 Bot Fight Mode / Super Bot Fight Mode 会把
openworker 这种程序化请求判成 bot 并返回挑战页，`/auth/*` 和 `/v1beta/*` 会直接不通
（`/login/*` 是真浏览器，不受影响）。这不是配置得越严越好的地方，具体见
[05-验证与排错.md](./05-验证与排错.md)。

## 平台风险

**SDK 内部机制风险（v2 已大幅收窄）**：v1 依赖 `GOOGLE_GEMINI_BASE_URL`
这个 google-genai SDK 内部实现细节做隐式接线，openworker 代码里毫无痕迹；
v2 改为在 `gemini_provider.py` 的 `_ensure_client()` 里显式传
`http_options=types.HttpOptions(base_url=...)`——这是 SDK 公开、优先级最高
的一等入口，中转地址从此有代码和测试背书。残余风险只剩调试通道：
`resolve_base_url` 里的环境变量分支仍读 `GOOGLE_GEMINI_BASE_URL`，SDK
升级不影响它（读取在 openworker 自己的代码里），但升级 SDK 后仍建议重走
一遍 [05-验证与排错.md](./05-验证与排错.md) 的验证阶梯。

**版本锁定建议**：当前确认可用的运行环境是 `google-genai==2.16.0`
（安装在 hermes-agent venv 下），而项目 `pyproject.toml` 目前只约束
`google-genai>=1.0`，上限完全开放。建议在部署环境里显式钉住
`google-genai==2.16.x`，充分验证新版本行为之后再放开升级。

**作用域风险（v1 遗留）**：v2 正常部署**不需要**设置任何环境变量——中转
地址内置在 openworker 自己的 provider 代码里，作用域天然只覆盖 openworker。
但如果本机还留着 v1 时代 `set-relay-env.ps1 -Install` 写入的 User 级
`GOOGLE_GEMINI_BASE_URL`，它会影响该用户下**所有**使用 google-genai 的
进程（同一台机器上的 hermes-agent 也会受影响），并且在 openworker 里会
**盖过**内置常量（调试覆盖的优先级更高）。不做调试时用
`set-relay-env.ps1 -Uninstall` 清掉它；临时调试用会话级的
`start-openworker-cn.ps1`。

**免费额度上限**：Cloudflare Workers 免费版是 100,000 请求/天、10ms
CPU 时间/次调用（流式等待上游响应的时间不计入 CPU，只有实际执行 JS
的时间算）、100MB 最大请求体、每次调用 50 个外部子请求。一次 Gemini
对话对应中转侧 1 个请求、1 个外部子请求，远低于这些上限；持续高频
使用才需要关注是否触顶。

**大陆可达性非保证**：以下三条均来自研究阶段的取证，置信度如实标注，
不夸大，也不做超出证据范围的保证：

| 结论 | 置信度 | 依据 |
|---|---|---|
| `*.workers.dev` 在大陆被 DNS 层面污染/阻断 | 中等 | 多个 Cloudflare 社区帖子一致报告，无官方声明 |
| 自定义域名一般比 `workers.dev` 可达，但不保证任何具体域名都能连通 | 低到中等 | GFW 具备基于 SNI 的定向阻断能力；未对 `smjtools.com`/`gemini.smjtools.com` 做过系统性实测 |
| `generativelanguage.googleapis.com` 本身在大陆受限 | 中等 | 多个二手来源一致报告，无权威一手来源 |

这也是本方案坚持只用自定义域名、完全不启用 `workers.dev` 的原因——但
即便如此也不构成「一定可达」的保证。以实测为准，验证方法见
[05-验证与排错.md](./05-验证与排错.md) 的五级验证阶梯；一旦中转不可达，
v2rayN + proxy-guard 的正向代理方案作为回退始终可用，两者互不冲突。

## 合规提示

Google 按地区限制 Gemini API 的使用；经中转访问相当于绕开这个地区限制，
属于用户自行承担的服务条款风险——这里只陈述事实，不做法律判断。

Key 与 `.env` 必须保密：研究阶段确认项目根目录的 `.env` 文件里有一个
自己的 `GEMINI_API_KEY`，绝不能提交进任何仓库、复制进任何文档或分享
出去。本目录下所有文档和示例代码中出现的 key 一律用占位符
`<YOUR_GEMINI_API_KEY>`，不会出现真实值。这把 key 的正式位置是**每个人自己
机器上**的 OpenWorker（设置 ▸ 模型 ▸ Gemini），中转不持有任何人的 key；本机
`.env` 里那份只对「绕开中转直连 Google」的调试场景还有用。

同样地，真实名单 `gemini-relay/scripts/roster.csv` 已在 `.gitignore` 里
——本仓库是公开 fork，同事的姓名和私人邮箱不进 git。
